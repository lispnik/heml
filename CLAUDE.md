# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Heml is an Emacs-style editor written in Common Lisp. It is a 2020 fork of Hemlock, the editor that was part of CMUCL, and was called Xoamax until 2026, when it and its code were renamed so as not to be confused with the upstream: the ASDF systems, packages and identifiers that said `hemlock` now say `heml` (`heml.base`, `heml-internals`, `heml:heml`). Hemlock itself is still named where the upstream or its history is meant.

It supports SBCL and ECL. Reader conditionals name only `sbcl` and `ecl`; code for other Lisps was removed. The Cocoa backend is SBCL only.

## Building and running

There is no unit test suite. `make smoke-tty` (`test/smoke-tty.sh`) runs the TTY backend in a detached tmux session, types into it with `send-keys`, and checks the screen with `capture-pane`. It then does the same for `heml:repl`, the `:mini` line-editing backend. `make smoke` (`test/smoke.lisp`) drives the Cocoa editor end to end and checks what it holds after each step: typing, input methods, split windows, resizing, the mouse, the clipboard, opening files, fonts, a shell, and a slave. It exits non-zero on a failure and leaves a picture of each step in `build/smoke/`. It neither activates the application nor uses the real clipboard, so it can run while someone is working. Add a check there when you add behaviour to the Cocoa backend. Neither script can run a single check. Each always runs its whole sequence. `make smoke-tty-ecl` builds under ECL and runs the TTY checks there (`LISP=ecl test/smoke-tty.sh`). `make demo` records a video of the TTY editor with `vhs` into `build/demo/`, from `scripts/demo/heml-tty.tape`. It covers SBCL, `heml:repl` and ECL. `make demo-cocoa` drives the Cocoa editor as the smoke test does (`scripts/demo/cocoa.lisp`), has the view render a frame ten times a second, and assembles the frames with `ffmpeg`. `make demo-full` makes both and joins them with title cards into `build/demo/heml.mp4` (`scripts/demo/combine.sh`).

Dependencies come from ocicl: `make deps` runs `git submodule update --init` and `ocicl install`, which restores what `ocicl.csv` lists into `ocicl/` (gitignored). That includes `objc` and `asdf-macos-app`. `conium` is the exception: `vendor/conium` is a submodule of lispnik/conium, branch `ecl`, whose ECL backend works on current ECL. `heml.base.asd` pushes it onto `asdf:*central-registry*`, which ASDF searches before ocicl. `vendor/jzon` is the other submodule, for the same reason (see Language servers). On macOS, `make run` opens the Cocoa editor from a fresh SBCL, and `make run-tty` runs the terminal editor in the current terminal (`LISP=ecl` for ECL). `make app` builds `build/Heml.app` with lispnik/asdf-macos-app, through `heml-app.asd`, which is kept separate so that loading `heml.cocoa` never needs asdf-macos-app. The bundle is signed ad hoc, or with `SIGN_IDENTITY` (`make app SIGN_IDENTITY="Developer ID Application: …"`), which reaches the `.asd` as `HEML_SIGN_IDENTITY`. A stamp file tracks freshness, and a record of the identity makes a change of identity rebuild. `make check-app` verifies the signature and `Info.plist`, and reports whether anything is linked from outside the bundle. The bundle holds the TTY backend too, and `Contents/Resources/bin/heml` (from `scripts/heml`, a `:bundle-resources` entry) is the command a shell runs: `make install-cli` links it into `CLI_DIR` (default `~/.local/bin`). The bundle's executable is the stock SBCL runtime, which reads its own options, prints its banner, and honours `SBCL_HOME` before it loads the core, so the launcher passes `--core` explicitly and `--noinform --end-runtime-options`. `heml.cocoa:main` sends output to the terminal when standard input is one (otherwise asdf-macos-app's log gets it), finds files from the shell's directory unless that is `/`, and starts slaves the way the launcher starts the app. asdf-macos-app copies resources without their mode, so the app recipe makes the launcher executable after the build; permissions are not part of the seal. `make smoke-cli` (`test/smoke-cli.sh`) checks the command, and CI runs it after building the app. `make dmg` makes `dist/Heml-<version>-<arch>.dmg`. `make notarize`, `make notarize-dmg` and `make release` notarise through `macos-app:notarize` with the notarytool keychain profile `NOTARY_PROFILE` (default `heml`); `notarize` refuses an ad hoc bundle or one that links outside itself. `RELEASING.md` has the whole procedure. `make clean` removes `build/` and `dist/`.

AppKit needs the process's main thread. To run Cocoa from a REPL, use `(asdf:load-system :heml.cocoa)` and then `(heml:heml nil :backend-type :cocoa)`, in a terminal SBCL's REPL. A SLIME or Sly REPL thread won't work.

From a REPL (the usual development loop):

```lisp
(push #p"/path/to/heml/" asdf:*central-registry*)
(asdf:load-system :heml.tty)
(heml:heml)                 ; or (ed)
```

Quicklisp also works: `(ql:quickload :heml.tty :verbose t)`.

Standalone SBCL binary: `./build.sh` builds `./heml` with the TTY backend. It runs Lisp via `$SBCL`, which defaults to `clbuild lisp`, so set `SBCL=sbcl` if you don't use clbuild. `./heml --help` lists the options, including `--backend tty|cocoa` (or `--tty`, `--cocoa`). `ttyheml.sh` and `dist.sh` are legacy clbuild scripts.

Runtime requirements: iolib needs `libfixposix` (`brew install libfixposix` on macOS). If CFFI can't find it, run `(push "/usr/local/lib/" cffi:*foreign-library-directories*)`. The editor picks Cocoa if `heml.cocoa` is loaded, and TTY otherwise (`choose-backend-type` in `rompsite.lisp`).

ECL notes:
- ECL reads every `--eval` on its command line before it evaluates any, so a later `--eval` can't name a Heml symbol. Use `uiop:symbol-call`, as `test/smoke-tty.sh` and the ECL slave command in `eval-server.lisp` do.
- ECL compiles through C, so a first build takes a minute or two.
- `heml.base.asd` works around two ECL problems. It gives ECL on macOS the `:bsd` feature that SBCL has, which osicat and the TTY backend expect; ASDF doesn't recompile when features change, so clear ECL's fasl cache if osicat was built without it. It also defines `ecl_to_cl_index` as `ecl_to_index` for the C compiler, working around an ECL 26.5.5 code-generation bug.
- An ECL `ffi:c-inline` result of `:unsigned-char` is a character: return a C `unsigned char` as `:int`.
- CFFI on ECL passes variadic arguments as fixed ones, which breaks on arm64 macOS. `terminal-size` (`tty-disp-rt.lisp`) therefore calls `ioctl` from C through `ffi:c-inline`. Do the same for any new variadic C call on ECL.

`test/smoke.lisp` shows how to drive the editor without watching it. It posts descriptors with `heml.cocoa::post-to-editor`, such as `(list :char #\x '("Meta"))` or `:quit`. It sends real NSEvents to the window, and has the view render itself to a PNG. `screencapture` needs Screen Recording permission, which a terminal usually lacks. A synthesized key-down cannot enter a dead-key state, so dead keys need a real keyboard.

## Architecture

**ASDF systems.** `heml.base.asd` is the backend-independent core. Each backend is its own system that depends on it:
- `heml.tty`: terminfo/termcap terminal display (`tty-*.lisp`, `terminfo.lisp`, `linedit.lisp`)
- `heml.cocoa`: native macOS backend through the `objc` bridge (`cocoa-*.lisp`), SBCL only

`heml.tree-sitter` (highlighting, indentation and the language modes) and `heml.lsp` (the language-server client) are systems of their own that the backends load.

`ioconnections.lisp` (the iolib event loop and connections) is the last module of `heml.base`. On SBCL it compiles at `(speed 2)`, from its own `declaim`.

All sources live flat in `src/`. Module membership and load order are defined only in the `.asd` files. When you add a file, register it in the right module. `core-2` is `:serial t`, so position matters there.

**Layers within `heml.base`.**
- `core-1`/`core-2`: the text model (`line`, `htext1-4`, `buffer`, `ring`), Heml variables (`vars`), the command interpreter (`interp`), `syntax`, search, and the redisplay model (`window`, `winimage`, `linimage`, `screen`, `display`, `cursor`). It also holds `connections.lisp` and `rompsite.lisp`, which are the event-loop and I/O abstractions.
- `wire`: an RPC layer (`wire`, `remote`, `port`) for talking to slave Lisps and eval servers.
- `root-2`: `main.lisp` (entry points and command-line parsing), `echo`, `streams`, `font`.
- `user-1`: all user-facing commands and modes, including file commands, Lisp mode, the REPL/eval server, spell, dired, bufed, shell and so on. `bindings.lisp` holds the default keymap and is loaded last.

**Packages** (`src/package.lisp`):
- `heml-internals` (nickname `hi`): the core.
- `heml-interface`: the public extension API, re-exported through `hi`.
- `heml`: commands and modes.
- `heml-ext`: portability shims.
- `heml.wire` (nickname `wire`), `heml.terminfo`, and `heml-user`, where user init code runs.

When you use a new internal symbol from another package, export it from `package.lisp`.

**Backend dispatch.** `call-with-editor` in `main.lisp` picks a backend keyword (`:tty`, `:cocoa`) and dispatches through generic functions specialized with `(eql :backend)`: `backend-init-raw-io`, `%init-screen-manager`, `make-event-loop`, `dispatch-events-with-backend`, and so on. Both share the iolib event loop. To see what a backend must provide, grep for `(eql :cocoa)`.

**Redisplay is never incremental.** Each redisplay rebuilds every visible window's image from its display start (`update-window-image` in `winimage.lisp` fills the dis-lines through `compute-line-image`). The device then draws all of it through its single `device-redisplay` method. Nothing records what changed, so nothing can be left stale. `compute-line-image` calls the buffer's mode's highlighter (`highlight-line`), which keeps syntax highlighting current on every line shown. The TTY device writes every row and clears each one to the end of the line, with no clear beforehand, so it doesn't flicker. Its output goes to the terminal's fd synchronously (`write-and-maybe-wait`), because redisplay often runs inside an event handler (for example, a shell's output) where dispatching events again isn't safe. Redisplay entry points return NIL when they have drawn: the input loop redisplays again while one returns true.

Each pass is bracketed by `device-begin-redisplay` and `device-end-redisplay` (`with-device-redisplay` in `display.lisp`). On the TTY these wrap the frame in synchronized output (DEC mode 2026, turned off by `*tty-synchronized-output*`) and hide the cursor while drawing. Where `civis` is DECTCEM, the cursor is shown again with DECTCEM alone, because `cnorm` can do more, such as xterm's turning off a blinking cursor. Redisplays caused by events are at most `*redisplay-interval*` (1/60 s) apart. The input loop waits out the rest of that interval for more events before it draws again, and ordinary stream output (`redisplay-windows-from-mark` with THROTTLEP) skips drawing within it. An explicit `finish-output` or `force-output` still draws at once. When idle, the loop waits for input only until the next event `schedule-event` queued is due (`next-scheduled-event-wait`, exact rather than rounded, so that it never polls), so scheduled events run on time rather than at the next keystroke.

The backend keyword is also mapped to a connection backend in two `ecase` forms: `%call-with-editor` in `main.lisp` and `%start-slave` in `eval-server.lisp`. A new backend must be added to both.

**Syntax highlighting** belongs to a buffer's major mode. `define-mode-highlighter` (`exp-syntax.lisp`) names a function of a line that brings its font marks up to date, and `compute-line-image` calls it, through `highlight-line`, for each line it draws. A mode that names none is not coloured. `heml.base` gives Lisp mode `line-tag`, the hand-written Lisp parser in `exp-syntax.lisp`. Tags are also computed for their package, which the modeline shows in every buffer, so `recompute-syntax-marks` makes marks only where `lisp-highlighted-p`. `heml.tree-sitter` (`tree-sitter.lisp`, `tree-sitter-modes.lisp`; SBCL and ECL, loaded by the TTY and Cocoa systems) highlights with tree-sitter. Its interface passes a 32-byte node struct by value, which CFFI cannot, so the `ts` macro calls a function through `sb-alien` on SBCL and through a function pointer in `ffi:c-inline` on ECL; memory is CFFI's, and libraries are loaded with `sb-alien:load-shared-object :dont-save t` on SBCL, since CFFI's loader there runs on the initial thread, which Cocoa's main loop holds. `define-tree-sitter-language` ties a grammar to a mode: C, Markdown, Python and Shell Script (Bash's grammar) are modes of their own, Pascal mode (Hemlock's) is coloured by Pascal's grammar, and Lisp mode uses tree-sitter's Common Lisp grammar with `line-tag` as its `:fallback`: the first time the grammar is needed and cannot be loaded, the mode goes back to `line-tag` for good. `line-tag` colours strings, comments (`#| |#` too), keywords and definition names. `define-mode-highlighter` resets every buffer's tag line so that tags computed under the other highlighter are computed again. Why a language could not be loaded is kept in its `problem` slot, never printed: the terminal editor's error output is its screen. A buffer is parsed again when its `buffer-signature` changes, incrementally: `edit-tree` compares the old text with the new, tells the old tree the one span that changed (`ts_tree_edit`), and the parse reuses it; and a line is coloured from the highlight query's captures within its bytes; `*capture-fonts*` maps capture names to colours, and a language's `:precedence` says whether the first or the last of two patterns on the same text wins (tree-sitter's queries and Neovim's differ). With `:indent`, a language also indents its mode's lines (`tree-sitter-indent-line`, the mode's "Indent Function", with spaces): `indent-column` follows Neovim's algorithm over the language's `indents.scm` (`@indent.begin`, `.branch`, `.end`, `.dedent`, `.align`, `.auto`, `.ignore`, `.zero`, and `#set!` settings), from the node the line starts with, or for a blank line the one the line before ends with. Code being typed parses as errors, so inside an ERROR, and on a blank line after one that `:finishes` a block (Python's `return`), `textual-indent` works from the line before instead: a level more if it `:opens` a block, less if this line `:closes` one, from the line its statement began on (`statement-start`, by parentheses). Return is "New Line and Indent" in C, Python, Shell Script and Pascal, which indents the line it leaves too, and `}` indents in C. Neovim's queries serve C, Pascal and Python; Bash's is Heml's own (`scripts/tree-sitter-queries/bash/indents.scm`). The library, grammars and queries are found at run time in `*tree-sitter-directories*`, each laid out as Homebrew lays them out; without them a buffer is simply not coloured. Markdown is two grammars: the block grammar leaves the text of headings, lists and paragraphs in `(inline)` nodes, which `parse-inline` parses again with the inline grammar (the language's `:inline`), limited to those ranges with `ts_parser_set_included_ranges`; `line-fonts` lays down the block query's spans and then the inline query's, and `merge-fonts` lets an inner style add to an outer one (`***both***` is bold and italic). `make tree-sitter` builds the C, Markdown (block and inline), Pascal, Bash and Common Lisp grammars into `build/tree-sitter/` (`scripts/tree-sitter-grammars.sh`, pinned tags); the library and Python's grammar come from Homebrew (`brew install tree-sitter tree-sitter-python`). `make install-tree-sitter` copies the grammars to `$XDG_DATA_HOME/heml/tree-sitter/` (`~/.local/share/heml/tree-sitter/`, `TREE_SITTER_DIR`), where the installed app finds them.

A language's `:definitions` are the node types (C's `function_definition`, Python's classes too, Pascal's `defProc`) that `definition-spans` finds by walking the tree: `C-M-a`, `C-M-e` and `C-M-h` ("Beginning of Definition" and its fellows) move by them in those modes, and "Outline" lists them, or a Markdown buffer's headings, in the result buffer `*Outline*`. `tree-sitter-modes.lisp` also holds each language mode's commands and menu: "Find Other File" (C's header or source, `C-c o`), "Shift Region Right"/"Left" (Python, `C-c >`/`C-c <`), "Python Run File", "Shell Script Run File" and "Pascal Compile File" (`C-c C-c`, into the compilation buffer; Pascal's grammar knows Delphi's and Free Pascal's dialects, and `fpc`'s `x.pas(3,5) Error:` lines are places), "Send Region to Shell" (`C-c C-r`), Markdown's heading commands (`C-c C-n`, `C-c C-p`, `C-c =` and `C-c -`), and "Markdown Fill Paragraph" (`M-q`), which hangs a list item's lines under its text and keeps a quotation's `>`. A language's `:single` names a line that governs one statement (Pascal's `then`, `do` and `else`): after that statement, `textual-indent` goes back to the governing line's indentation.

**Result lists** (`results.lisp`): a buffer listing places, one a line, has the buffer variable "Result Location Function", a function of a line that returns `(pathname line column)` or `(pathname :position n)`, or NIL for a header; `plist-line-location` reads a place kept in the line's plist, for lists that never change. In every result mode Return visits the place in the other window, `n` and `p` show the next and previous, `C-o` shows it, and `q` buries the list; ``C-x ` `` ("Next Result") visits the next place of the list made last, `*result-buffer*`, from anywhere. Grep, Compilation, Xref and Outline are result modes. Grep and Compile (`grep.lisp`) run a command ("Recursive Grep" asks only for a pattern and a directory, and uses `rg` when it is installed) with its own filter and sentinel, writing to the end of the buffer, never at point; the sentinel writes the count, and must not redisplay (no `message`), since it runs inside an event handler. A line `file:line:[column:]` names a place; Compilation also reads Python's `File "x", line N` and a shell's `x: line N:`. Grep colours the file, line number and what matched, from the pattern `grep-pattern-scanner` reads out of the command. `C-x C-q` makes a Grep buffer Wgrep, where `C-c C-c` writes each changed line to its file's buffer (it checks the line there is still what grep found) and `C-c C-k` puts them back. Setting `(current-window)` does not change the current buffer: go to a window with `select-window`, or `change-to-buffer` after it.

The other list modes build their lines from state and keep each line's entry in its plist, with a highlighter of their own: Apropos (every kind a symbol names, space describes, `.` visits), Debug (a frame's locals and source are gathered while the slave is in the debugger; Return shows the locals, `.` the source), Slave-List (a header and each slave's state), and Completelist and Fuzzylist (what the completions share, the next character, and a fuzzy match's characters).

**Projects** (`project.lisp`): a file's project is the nearest directory above it holding one of `*project-markers*` (`.git`, `.hg` and the like), or else the nearest holding one of `*project-build-markers*` (`Makefile`, an `.asd`, `package.json` and the like); `project-root` caches the answer by directory, and the home directory and `/` are never roots. `project-files` asks `git ls-files`, then `rg --files`, then walks the tree. `C-x p` holds the commands, as in Emacs ("Previous Window" moved to `C-x O`): `f` finds a file (completion over the project's files; text that is no file's name finds those with its characters in order, ranked by `fuzzy-file-score`, and lists several in `*Project Files*`, the best first), `g` greps and `c` compiles at the root (the last command kept per project), `s` a shell there, `!` a shell command, `d` Dired, `p` switches project, `b` a project buffer, `l` Bufed filtered to the root (a Bufed filter starting with `/` is a directory), `r` replaces a string in every file that has it ("Project Replace": the files from `rg -l -F`, the count asked about, the edits made in the files' buffers, the changed lines listed in `*Project Replace*`, then the buffers saved if wanted), `k` kills the project's buffers, `F` forgets it, `e` edits its settings. A file `.heml-project` at the root, a property list read as data (`project-settings`, read again when the file changes), also makes its directory a root: `:name` is what the modeline shows, `:compile` what `C-x p c` offers at first, `:ignore` the files `C-x p f` leaves out (`dir/`, `*.ext` or a path's start), and `:variables` an alist of Heml variable names and values set in each of the project's file buffers. Projects become known through "Buffer Pathname Hook" and are kept, with each project's session, in `*project-state-directory*` (`$XDG_STATE_HOME/heml/`, or `HEML_STATE_DIRECTORY`; the tests set it; what an older Heml kept in `~/.heml/` is moved there the first time). A session is the project's files, their points, and the window layout as `device-layout`'s tree, whose windows show a file, one of the project's directories in Dired, or its shell; it is saved on leaving a project with `C-x p p` and on exit ("Exit Hook"), and restored on switching to it and, through "Entry Hook", on starting with no files in a project. "Project Sessions" turns that off. A session also holds what was typed to the project's shell (`:shell-history`, put back in the shell's "Interactive History" when `project-shell` starts it), and the project's compile commands are kept in its entry in `projects.lisp` (`:compile-history`): `C-x p c` binds `*echo-area-history*` to them, so `M-p` at its prompt goes back through them. `recent-files.lisp` in the same directory lists the files visited, the latest first (`note-recent-file`, on "Buffer Pathname Hook"); `C-x C-r` is "Find Recent File", with the same fuzzy matching as `C-x p f` ("Insert File" is `C-x i`, as in Emacs). The modeline's `:project` field, after the modes, shows `[name]`.

**Completion at point** (`popup.lisp`): "Complete at Point" (`C-M-i`, and Tab in a word through "Indent Or Complete" and "Completion Function") asks the mode's "Completions Function" for the completions of what is before point and where it starts -- Lisp's symbols from the slave (`eval-form-in-server-1`) or the editor's image, and the buffers' tokens (each with its kind as a note: a completion is a string or `(string . note)`); in a shell buffer file names, from the shell's directory; elsewhere the buffers' words -- and `popup-choose` shows them in a popup under point, reading keys itself as incremental search does: `C-n`/`C-p` or the arrows choose, Return or Tab puts the choice in, typing narrows, anything else is put back and ends it. At a file prompt, Tab on an ambiguous name shows the files in a popup at the foot of the window above (`choose-file-completion`, `bottom-window`). "Complete as You Type" (a variable and a command) brings the popup up by itself, through "Self Insert Hook", once a word is "Complete as You Type Length" long; then only Tab puts a choice in. The popup is device-independent: `*popup*` (`winimage.lisp`) is rows of text and a font each, and `update-window-image` lays them over the window's dis-lines (`overlay-popup`, `linimage.lisp`), adding dis-lines past the buffer's end (whose `dis-line-line` is NIL) when it needs them.

**Language servers** (`lsp.lisp`, the system `heml.lsp`): a client for the Language Server Protocol. `define-language-server` names, for a major mode, the commands that run a server (the first whose program `find-program` finds is used) and the protocol's language id; C has `clangd`, Python `pyright-langserver`, `pylsp` and others, Shell Script `bash-language-server`, Pascal `pasls`. A server is one process for a mode and a project's root (`buffer-language-server`), started by `lsp-idle`, a scheduled event twice a second, for the current buffer, when "Language Servers" is true; it is a process connection whose filter (`lsp-receive`) collects bytes into messages by their `Content-Length` and whose error output is discarded. JSON is jzon's: objects are hash tables with string keys (`json`, `jref`), arrays vectors, false NIL, null the symbol `NULL`. The buffer's text is sent on opening, and when `buffer-signature` has changed its change is (`lsp-sync`, before every request and from `lsp-idle`): to a server whose `textDocumentSync` is incremental, the one span that differs between the text last sent, kept in the buffer's `document`, and the text now (`text-change`, by their common start and end); to another, the whole text. A request (`lsp-request`) waits for its answer in `lsp-wait`, dispatching events, and gives up after its timeout; positions are lines from 0 and UTF-16 code units (`lsp-position`, `lsp-move-mark`). `publishDiagnostics` becomes marks in `*buffer-diagnostics*` and is drawn through `hi:*line-decoration-functions*`: a function of a line returning `(start end font)` lists, which tree-sitter's `line-fonts` lays over its colours, drawing the line again when `hi:*decoration-tick*` has changed. In a served mode `M-.` is "LSP Find Definition", `M-?` "LSP Find References" (a result list), `C-c C-d` "LSP Describe" (the error on the line and the hover text, in `show-text-popup`, a popup until the next key), and the mode's "Completions Function" is `lsp-completions`, the server's items with their kinds for the completion popup, or the buffers' words when it has none; `C-c C-a` is "LSP Code Action": the server's fixes and refactorings for what is wrong at point, chosen from `popup-select` (a popup menu: `C-n`/`C-p`, a digit, Return), and done by making the action's edit (`apply-workspace-edit`) or by `workspace/executeCommand`, whose edits the server asks for with `workspace/applyEdit`, answered in `lsp-dispatch`. "Outline" asks `*outline-functions*` first, where `lsp-outline-entries` gives the server's `documentSymbol`s with their kinds. "LSP Rename", "LSP Format Buffer", "LSP Diagnostics" and "LSP Restart" are commands and items of the mode's menu. In Lisp mode the same keys are the slave's: `M-.` "Find Definitions", `M-?` "Who Calls", `C-c C-d` "Describe Symbol". `HEML_LSP_LOG` names a file every message is added to. jzon comes from `vendor/jzon`, a submodule of Zulu-Inuoe/jzon that `heml.lsp.asd` pushes onto `asdf:*central-registry*`: the jzon ocicl has (20251113-f05afbb) does not compile under ECL (its `native-namestring` uses UIOP's `os-cond`, `os-unix-p` and `unix-namestring` unqualified on Lisps other than SBCL, CCL and CMUCL), and jzon's fix, 703cb7e, is later. When ocicl has a jzon with it, the submodule can go and `com.inuoe.jzon` go back into `ocicl.csv`. Both backends load `heml.lsp`, on SBCL and ECL. `test/fake-lsp.py` is the server the smoke tests check the client against: `test/smoke.lisp` in Cocoa, and `test/smoke-tty.sh` in the terminal under SBCL and ECL, each naming it as Pascal's server for the run.

**Spelling.** The dictionary is built in memory from `resources/spell-dictionary.text`, which `spell-build.lisp` reads into the image at compile time (`build-dictionary-in-memory`): its hashes are the Lisp's own `sxhash`, so no binary file travels between Lisps. In Text mode with Spell mode on, `text-highlight-line` (`spellcoms.lisp`) underlines each word the dictionary lacks in red, and shows links.

**Shells and interactive buffers.** `get-interactive-input` records where each input began ("Input Starts"): `C-c C-p` and `C-c C-n` ("Previous Prompt", "Next Prompt") move between them, and Return on an earlier input sends it again. A shell buffer keeps at most "Shell Output Limit" lines (20000), trimming its start, and a carriage return in its output clears the output line, not the line at point.

**Links** (`exp-syntax.lisp`): `line-links` finds a line's links in its text (Markdown `[text](url)`, `<url>`, bare URLs, trailing punctuation trimmed), and each is drawn in `link-font`, a font whose `:link` key holds the target. Tree-sitter's `line-fonts` lays links over its colours; a mode with no highlighter gets `highlight-links`, which leaves alone a line with font marks of its own (a shell's colours). The TTY sends a font with `:link` as an OSC 8 hyperlink. "Open Link" (`C-c C-o`, `morecoms.lisp`) follows the link at point (`link-at-mark`): a web or mail address with `open`, a file by visiting it; in Cocoa, Command-click does ("Mouse Open Link").

**Choosing a mode for a file** (`process-file-options`, `filecoms.lisp`): a `-*- Mode: … -*-` line wins; otherwise the file's type, through `define-file-type-hook`; otherwise, for a file without a type, the interpreter its `#!` line names, through `define-interpreter-mode` (`#!/bin/sh` and `#!/usr/bin/env bash` are Shell Script, `python3` is Python, `sbcl` is Lisp; a version such as `python3.12` is dropped). `define-comment-syntax` (`tree-sitter-modes.lisp`) sets a mode's "Comment Start", "Comment End" and "Comment Begin".

**Dired** (`diredcoms.lisp`, with file operations in `dired.lisp` and the listing in `print-directory-verbose`, `filecoms.lisp`). A Dired buffer is a header line and then a line per file, in the order of `dired-info-files`; `dired-file-at` and `dired-file-line` map between them, skipping `+dired-header-lines+`. A file's first column shows its state: `D` flagged for deletion (`dired-file-deleted-p`), `*` marked (`dired-file-marked-p`). Operations act on `dired-targets`: the marked files, or the one under point. `update-dired-buffer` keeps marks, flags and point's file. Deleting moves files to the Trash with `/usr/bin/trash` where it exists ("Dired Delete to Trash"). A scheduled event (`start-dired-watch`) calls `maintain-dired-consistency` every two seconds, which lists a directory again when `dired-directory-signature` (its modification time and size, since the time is kept to the second) has changed. `*directory-sort*` orders the listing by name, date or size. `i` lists a subdirectory inline (`dired-info-expanded`): `dired-listing` puts its entries after its line, named from the top directory (`sub/file`, through `*directory-name-prefix*`), so each line is still one file. `C-x C-q` switches the buffer to Wdired, a major mode of its own so that letters are letters, keeping the buffer's `dired-information`; `C-c C-c` renames each file whose name its line now shows differently (`dired-line-name`), and `C-c C-k` goes back to Dired. The watcher leaves a Wdired buffer alone. `define-mode-highlighter` colours Dired's lines (`dired-highlight-line`).

**Bufed** (`bufed.lisp`, `C-x C-b`) lists the buffers under a header, one a line: a mark column (`*` marked, `D` flagged), then `.` current, `%` read-only and `*` modified, and the name (just the file's name when the buffer has the default name for its file), size, mode and file. The list is made again from the buffers (`bufed-fill`) whenever it is shown; `*bufed-lines*` holds what each line after the header shows, an entry or NIL for a group's heading; marks live in `*bufed-marks*`, by buffer, so they survive. Operations act on `bufed-targets`. `*bufed-sort*` (recency, from `*buffer-history*`; name; size; mode), `*bufed-filter*` (a mode's name, which wins over name text, `*` for modified, or text in names) and `*bufed-grouped*` (by directory) shape it. Buffer hooks only mark it stale; a scheduled event makes it again within a second while it is shown.

**Menus** (`menus.lisp`) are data, for whichever frontend shows them: `define-menu`, `add-menu-item`, `remove-menu-item`, `remove-menu` and `define-context-menu`, exported from `heml-interface`, change `*menus*` and `*context-menus*` and call the functions in `*menu-change-functions*`. An entry is `(title action &key key modifiers hidden)` or `:separator`; the action is a command's name, `(:command name arg ...)`, or what only a frontend can do (`(:call function)`, `(:selector "name:")`, `(:font-size n)`, `:services`). A menu's `:mode` shows it only in that major mode's buffers; its `:role` (`:application`, `:windows`, `:help`) is for the frontend. The built-in menus are defined there. "Menu Bar" (`M-\``) picks a menu and an item in the echo area, the terminal's way to them.

**The Cocoa backend's threads.** AppKit must own the main thread, so `invoke-with-editor-thread :cocoa` (`cocoa-main.lisp`) runs `[NSApp run]` there and runs the whole editor session on a thread named "Heml". The two threads never share Heml state:
- Input: `-keyDown:` posts plain descriptors to an inbox and writes a byte to a pipe. The pipe's read end is an ordinary iolib connection, and its filter turns the descriptors into key-events on the editor thread.
- Output: the device's redisplay methods copy dis-lines into the screen (a locked grid of rows). When a pass is finished, `device-force-output` calls `present-screen`, which copies the rows and cursor into the screen's `shown-` slots, and `-drawRect:` paints only those. So the view never shows a frame half drawn.
- Typing: named keys, and keys with Control or Meta, are posted directly from `-keyDown:`. Everything else goes through `-interpretKeyEvents:` and the view's `NSTextInputClient` methods, so dead keys and input methods work. Only the left Option key is Meta by default.
- The clipboard: `*interprogram-cut-function*` and `*interprogram-paste-function*` (`killcoms.lisp`) join the kill ring to the pasteboard. Kills and "Save Region" call the first; "Un-Kill" calls the second, and uses the pasteboard only if its change count shows another application wrote to it. The Edit menu posts Super keys, which `install-mac-bindings` binds.
- Menus are Heml's (`menus.lisp`, below); Cocoa adds its application and Window menus and its Mac-only items through the same API, and `rebuild-main-menu` builds the menu bar from `copy-menus` on the main thread whenever `*menu-change-functions*` says they changed. A mode's menu is shown only while the current buffer is in that major mode: each frame carries the mode (`screen-mode`, left alone while the echo area prompts), and `present-screen` has the main thread call `show-mode-menus` when it changes. The item's tag indexes `*menu-actions*`. A command is posted as `(:command name arg ...)`: the editor queues it in `*menu-commands*` and then the `Menucommand` key, and the "Menu Command" command runs it. So a menu item runs inside the command loop, with prompts, undo and errors behaving as they do for a typed key.
- Files from Finder arrive at the app delegate's `application:openURLs:` and are visited through `process-command-line-argument`.
- Fonts: fonts belong to the main thread. `change-font` re-measures the cell and posts a `:resize`, and it saves the choice in `NSUserDefaults`. The View menu's items target the app delegate, not the responder chain, so their shortcuts work whatever has focus.
- Anything AppKit must do for the editor thread goes through `on-main-thread`.

**Window layout** is shared by every device (`layout.lisp`). The windows other than the echo area tile a rectangle, and `device-layout` holds that as a tree: each leaf is a hunk, and each split divides its space into rows or side-by-side columns, with a size for each child. Side-by-side windows are divided by a column that neither owns, and each device draws a bar there. The shared `device-make-window`, `device-delete-window` and `device-enlarge-window` methods change the tree. `apply-layout` then sets every hunk's geometry, resizes each window's image to fit, and rebuilds the ring of hunks in tree order, which is the order `next-window` follows. `resize-device-layout` handles a new screen size. A device only supplies `device-make-hunk` and draws each hunk where the hunk says: `device-hunk-column` and `device-hunk-width` give its columns, its `position` is its modeline row, and its text starts at `text-position - text-height + 1`. `C-x 3` is "Split Window Horizontally", `C-x {` and `C-x }` shrink and enlarge a window horizontally, `C-x 1` is "Delete Other Windows", and `C-x +` is "Balance Windows" (`balance-layout`), which sizes each split's children by how many windows lie across each one.

**The mouse.** Heml represents the mouse as key-events with mouse keysyms: `Leftdown`, `Leftup`, `Leftdrag`, `Scrollup`, `Scrolldown` and the others in `keysym-defs.lisp`. A backend queues each one with `q-event`, passing the X and Y within the window's text (Y is NIL on a modeline) and the hunk. Pointer commands read them back with `last-key-event-cursorpos`. The Cocoa view posts grid cells, and `locate-cell` on the editor thread turns them into those coordinates. On its first entry, Cocoa rebinds the left button to the "Mouse ..." commands in `morecoms.lisp`, and gives the active region the `:selection` background. Dragging the bar between side-by-side windows, or a modeline, resizes windows: `drag-border` (`cocoa-device.lisp`) intercepts that press and its drags before they become keys, and moves the edge with `layout-move-edge`. Each frame also carries the draggable edges (`layout-borders`) to the main thread, where `-resetCursorRects` gives them resize cursors.

**Where Heml keeps things** follows the XDG Base Directory specification (`main.lisp`): `heml-config-directory` is `$XDG_CONFIG_HOME/heml/` (`~/.config/heml/`), `heml-state-directory` `$XDG_STATE_HOME/heml/` (`~/.local/state/heml/`), and `heml-data-directory` `$XDG_DATA_HOME/heml/` (`~/.local/share/heml/`); a variable unset, empty or relative is ignored. The init file is `~/.config/heml/init.lisp`, or failing that the older `~/.heml.lisp`, `~/.heml/heml.lisp` or `~/.heml-init.lisp` (`init-file-names`, `init-file`). The Cocoa app's Settings… opens `init-file`, making its directory.

**The environment and file names.** An app started by Finder has the system's short `PATH`, so, as Emacs's exec-path-from-shell does, `maybe-import-shell-environment` (`main.lisp`, before the init file is loaded) runs the user's login shell (`login-shell`: `$SHELL`, or the password file's) as `-l -i -c /usr/bin/env` and sets `*shell-environment-variables*` (`PATH`, `MANPATH`, the locale and the agents' sockets) in the process, which the programs Heml runs inherit; `*import-shell-environment*` is `:auto` (only when there is no `TERM`, that is, not started from a terminal), T or NIL, and "Import Shell Environment" does it again. "Shell Utility" is NIL for the user's own shell. `heml-ext:expand-file-name` reads a file name as a shell would: `~` and `~user` are home directories (`isys:getpwnam`), and, since a file prompt starts with a directory in it, a `~` after a `/` or a second `/` starts the name again, as in Emacs. The file prompt (`file-verification-function`), file completion (`complete-file`), `find-file-buffer`, a shell buffer's filename completion and "Open Link" all go through it.

**Extending the editor.**
- A variable's or a command's name is a string literal: never change one in place (`canonical-case` copies; it once upcased its argument, which renamed a command that shared a variable's name).
- Commands are defined with `defcommand "Name" (p) ...`, which produces a function called `name-command`.
- Editor variables are defined with `defhvar`.
- Keys are bound with `bind-key "Command Name" #k"control-x"`.
- Modeline fields come from `make-modeline-field` (`window.lisp`).

Useful globals include `hi::*buffer-list*` and `hi::*window-list*`.

**Characters.** Buffer lines are full `character` strings, and files are read and written as UTF-8. Heml shadows `char-code-limit` as 256 in `heml-ext` and `hi`, so a table indexed by character code covers only the first 256 codes. Past that, character sets fall back to a hash table (`char-set-ref` in `charmacs.lisp`), and so do `char-key-event` and the Boyer-Moore jump tables, which use the low byte. Don't declare a `base-char`: on SBCL that means ASCII.

A key for a character past ASCII comes from `heml-ext:character-key-event`, which makes the key-event on first use. Its keysym is the code point for Latin-1, and `#x01000000` plus the code point past that, as in X11, so it can't collide with the special keys at `#xFF00`–`#xFFFF`. `*new-character-key-event-hook*` then binds it to Self Insert (`bindings.lisp`). Keysyms past 16 bits live in `*large-keysym-key-events*`. A wide character (East Asian Width W or F: CJK, fullwidth forms, most emoji) is displayed as itself followed by `wide-character-filler` (`linimage.lisp`). This goes through the same print-representation mechanism that shows a control character as `^X`, so everything that counts columns counts two. The character sets fill those entries lazily through `character-set-default-function` (`charmacs.lisp`). A device draws the character across both cells and nothing for the filler: TTY's `device-write-string` skips it, and so does Cocoa's `draw-text`.

**Font numbers are colours.** A font number in a font-change is an ANSI colour index, or a property list such as `(:fg 7 :bg 4 :bold t)` (`*modeline-font*` in `window.lisp`), whose keys are `:fg`, `:bg`, `:bold`, `:italic` and `:underline`. The TTY and Cocoa backends both read them that way. Cocoa keeps italic and bold-italic fonts beside the regular and bold ones (`install-fonts`); a font with no italic face is slanted instead (`NSObliqueness`, recorded in `display-slanted`). It draws an underline itself, a line at the baseline the width of the run's cells, rather than asking AppKit for one.

**Slave Lisps.** The binary re-executes itself with `--slave` to create eval-server slaves, which it talks to over `wire`. See `eval-server.lisp`, `lispeval.lisp` and `slave-list.lisp`.

**Terminals.** `heml.terminfo:tparm` evaluates terminfo string expressions, including the `%? %t %e %;` conditionals that every 256-colour terminal's `setaf` uses. Its binary operators pop their second operand first. The terminal's erase character (`*tty-erase-char*`, usually `^?`) is Backspace, whatever terminfo's `kbs` says. `setup-input` (`tty-disp-rt.lisp`) leaves `IEXTEN` on, so it disables VLNEXT, VDISCARD and VSTATUS itself. Otherwise the driver would swallow `C-v`, `C-o` and `C-t`. `linedit-device`, the `:mini` backend in `linedit.lisp`, has its own `device-init`, which starts without the alternate screen; the full-screen TTY editor uses the alternate screen. Shell buffers turn SGR colour sequences into font marks and drop other escape sequences (`write-shell-output` in `shell.lisp`).

**CI.** `.github/workflows/ci.yml` runs on a macOS runner, which has a window server. It checks out the submodule, sets up ocicl for SBCL and ECL, runs `make smoke`, `make smoke-tty` and `make smoke-tty-ecl`, builds and checks the app ad hoc, makes its disk image, and starts and quits the app. It uses Homebrew's SBCL, which links libzstd, so that bundle is for testing only. `.github/workflows/release.yml` runs on a tag `v*`, or by hand as a dry run. It builds SBCL `--without-sb-core-compression` (cached), then on arm64 and Intel runners signs with the Developer ID from the secrets, notarises and staples the app and the disk image, and publishes a release with both images.
