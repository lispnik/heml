# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Heml is an Emacs-style editor written in Common Lisp. It is a 2020 fork of Hemlock, the editor that was part of CMUCL, and was called Xoamax until 2026, when it and its code were renamed so as not to be confused with the upstream: the ASDF systems, packages and identifiers that said `hemlock` now say `heml` (`heml.base`, `heml-internals`, `heml:heml`). Hemlock itself is still named where the upstream or its history is meant.

It supports SBCL and ECL. Reader conditionals name only `sbcl` and `ecl`; code for other Lisps was removed. The Cocoa backend is SBCL only.

## Building and running

There is no unit test suite. `make smoke-tty` (`test/smoke-tty.sh`) runs the TTY backend in a detached tmux session, types into it with `send-keys`, and checks the screen with `capture-pane`. It then does the same for `heml:repl`, the `:mini` line-editing backend. `make smoke` (`test/smoke.lisp`) drives the Cocoa editor end to end and checks what it holds after each step: typing, input methods, split windows, resizing, the mouse, the clipboard, opening files, fonts, a shell, and a slave. It exits non-zero on a failure and leaves a picture of each step in `build/smoke/`. It neither activates the application nor uses the real clipboard, so it can run while someone is working. Add a check there when you add behaviour to the Cocoa backend. Neither script can run a single check. Each always runs its whole sequence. `test/smoke.lisp`'s `run` is one function, about as large as SBCL can compile in its default heap: put a new group of checks in a function of its own and call it, as `language-server-feature-checks` is. `make smoke-tty-ecl` builds under ECL and runs the TTY checks there (`LISP=ecl test/smoke-tty.sh`). `make smoke-lsp` (`test/smoke-lsp.sh`) runs the language servers themselves: it copies a small project for each language from `test/fixtures/lsp/` into `build/smoke-lsp/` (two or three files and a `.heml-project`; the main one has a function, forty lines of comment, then a call to another file's function, a call to its own, and one mistake), and in the TTY editor checks that the server's error is counted and listed, that `C-c C-d` describes the call, that `M-.` finds the definition, there and in the other file, and that `C-M-i` completes the name; JSON and YAML are checked for the error only, YAML also for a schema its project's settings name; C also for folding, callers and renaming, Rust for inlay hints, Python for a second server (ruff), and TypeScript and JavaScript for sharing one. A server that is not installed is skipped, or with `SMOKE_LSP_STRICT=1`, as in CI, is a failure; `SMOKE_LSP_ONLY="rust go"` runs only those; `LISP=ecl` runs it under ECL. What was said is in `build/smoke-lsp/lsp.log`. The tmux helpers both scripts use are in `test/tmux-lib.sh`. `make smoke-run` (`test/smoke-run.sh`) runs programs and their tests in Rust, Go, JavaScript and TypeScript from `test/fixtures/run/` (each prints `twice 21 is 42` and has a test that passes and one that fails; `rust-broken` does not compile), checking the output and that ``C-x ` `` visits the failure; a missing toolchain is skipped, or fails with `SMOKE_RUN_STRICT=1`. `make smoke-git` (`test/smoke-git.sh`) makes a repository in `build/smoke-git/repo` and checks the fringe's marks, the status buffer (a hunk and a file staged, a file unstaged, a commit, a change discarded), the log, a commit's diff and a line of it visited, the blame and a file's diff. Both `smoke-tty.sh` and `smoke.lisp` check the terminal emulator (bash, as "Term Program", without startup files: colours, its size, `less`, ^C, ^Z and job control, a smaller window, Term Copy mode, its end; Cocoa leaves pictures of it and of `less`), and the TTY one that `C-c C-c` interrupts a shell buffer's command. Send `C-g`, not Escape, to dismiss a popup that may not be there: an Escape with no popup is the next key's Meta. `make demo` records a video of the TTY editor with `vhs` into `build/demo/`, from `scripts/demo/heml-tty.tape`. It covers SBCL, `heml:repl` and ECL. The Cocoa demos, `make demo-NAME` for each of `cocoa`, `tree-sitter`, `languages` (clangd on a C project made for it), `projects` (Heml's own source), `run` (cargo, go and node, on `test/fixtures/run/`), `debug` (lldb-dap on a C program) and `git` (a repository made for it), are `scripts/demo/NAME.lisp`, each loading `scripts/demo/driver.lisp`: it drives the Cocoa editor as the smoke test does, has the view render a frame ten times a second into `build/demo/NAME-frames/` (and records the rate they really came at), `wait-for`s text on the screen rather than guessing how long a server takes, notes each step's `caption`, leaves through the menu command "Exit Heml" so that no prompt about changed buffers can hold it, and stops what the editor started (a server keeps the pipe of whatever ran it open). `scripts/demo/encode.sh NAME` makes the frames into `build/demo/heml-NAME.mp4` with the captions in a band below the editor (ffmpeg's `drawtext`, each caption's text in a file, so nothing needs quoting). `make demo-full` makes them all and the terminal's, and joins them with title cards into `build/demo/heml.mp4` (`scripts/demo/combine.sh`, which leaves out a part that was not made).

Dependencies come from ocicl: `make deps` runs `git submodule update --init` and `ocicl install`, which restores what `ocicl.csv` lists into `ocicl/` (gitignored). That includes `objc` and `asdf-macos-app`. `conium` is the exception: `vendor/conium` is a submodule of lispnik/conium, branch `ecl`, whose ECL backend works on current ECL. `heml.base.asd` pushes it onto `asdf:*central-registry*`, which ASDF searches before ocicl. `vendor/jzon` is another submodule, for the same reason (see Language servers), `vendor/sexp-edit` a third, shared with the Lisp Listener (see Lisp editing), and `vendor/vterm` (lispnik/vterm, a CFFI binding to libvterm, which ocicl does not have) the fourth, pushed onto the registry by `heml.term.asd`; libvterm itself comes from Homebrew (`brew install libvterm`) and is loaded when the first terminal is made. On macOS, `make run` opens the Cocoa editor from a fresh SBCL, and `make run-tty` runs the terminal editor in the current terminal (`LISP=ecl` for ECL). `make app` builds `build/Heml.app` with lispnik/asdf-macos-app, through `heml-app.asd`, which is kept separate so that loading `heml.cocoa` never needs asdf-macos-app. The bundle is signed ad hoc, or with `SIGN_IDENTITY` (`make app SIGN_IDENTITY="Developer ID Application: …"`), which reaches the `.asd` as `HEML_SIGN_IDENTITY`. A stamp file tracks freshness, and a record of the identity makes a change of identity rebuild. `make check-app` verifies the signature and `Info.plist`, and reports whether anything is linked from outside the bundle. The bundle holds the TTY backend too, and `Contents/Resources/bin/heml` (from `scripts/heml`, a `:bundle-resources` entry) is the command a shell runs: `make install-cli` links it into `CLI_DIR` (default `~/.local/bin`). The bundle's executable is the stock SBCL runtime, which reads its own options, prints its banner, and honours `SBCL_HOME` before it loads the core, so the launcher passes `--core` explicitly and `--noinform --end-runtime-options`. `heml.cocoa:main` sends output to the terminal when standard input is one (otherwise asdf-macos-app's log gets it), finds files from the shell's directory, but goes to the home directory when that is `/`, as it is when Finder or the Dock (launchd) starts the app, so that prompts, shells and terminals start there, and starts slaves the way the launcher starts the app. asdf-macos-app copies resources without their mode, so the app recipe makes the launcher executable after the build; permissions are not part of the seal. `make smoke-cli` (`test/smoke-cli.sh`) checks the command, and CI runs it after building the app. `make dmg` makes `dist/Heml-<version>-<arch>.dmg`. `make notarize`, `make notarize-dmg` and `make release` notarise through `macos-app:notarize` with the notarytool keychain profile `NOTARY_PROFILE` (default `heml`); `notarize` refuses an ad hoc bundle or one that links outside itself. `RELEASING.md` has the whole procedure. `make clean` removes `build/` and `dist/`.

AppKit needs the process's main thread. To run Cocoa from a REPL, use `(asdf:load-system :heml.cocoa)` and then `(heml:heml nil :backend-type :cocoa)`, in a terminal SBCL's REPL. A SLIME or Sly REPL thread won't work.

From a REPL (the usual development loop):

```lisp
(push #p"/path/to/heml/" asdf:*central-registry*)
(asdf:load-system :heml.tty)
(heml:heml)                 ; or (ed)
```

Quicklisp also works: `(ql:quickload :heml.tty :verbose t)`.

Standalone SBCL binary: `./build.sh` builds `./heml` with the TTY backend. It runs Lisp via `$SBCL`, which defaults to `clbuild lisp`, so set `SBCL=sbcl` if you don't use clbuild. `./heml --help` lists the options, including `--backend tty|cocoa` (or `--tty`, `--cocoa`). `ttyheml.sh` and `dist.sh` are legacy clbuild scripts.

Runtime requirements: iolib needs `libfixposix` (`brew install libfixposix` on macOS). If CFFI can't find it, run `(push "/usr/local/lib/" cffi:*foreign-library-directories*)`. The editor picks Cocoa if `heml.cocoa` is loaded, and TTY otherwise (`choose-backend-type` in `rompsite.lisp`).

ECL notes:
- ECL reads every `--eval` on its command line before it evaluates any, so a later `--eval` can't name a Heml symbol. Use `uiop:symbol-call`, as `test/smoke-tty.sh` and the ECL slave command in `eval-server.lisp` do.
- ECL compiles through C, so a first build takes a minute or two.
- `heml.base.asd` works around two ECL problems. It gives ECL on macOS the `:bsd` feature that SBCL has, which osicat and the TTY backend expect; ASDF doesn't recompile when features change, so clear ECL's fasl cache if osicat was built without it. It also defines `ecl_to_cl_index` as `ecl_to_index` for the C compiler, working around an ECL 26.5.5 code-generation bug.
- An ECL `ffi:c-inline` result of `:unsigned-char` is a character: return a C `unsigned char` as `:int`.
- A structure's `(setf accessor)` is not a function on ECL: define a `defstruct` before the code that sets its slots, or the call compiles to a function that does not exist.
- CFFI on ECL passes variadic arguments as fixed ones, which breaks on arm64 macOS. `terminal-size` (`tty-disp-rt.lisp`) therefore calls `ioctl` from C through `ffi:c-inline`. Do the same for any new variadic C call on ECL.

`test/smoke.lisp` shows how to drive the editor without watching it. It posts descriptors with `heml.cocoa::post-to-editor`, such as `(list :char #\x '("Meta"))` or `:quit`. It sends real NSEvents to the window, and has the view render itself to a PNG. `screencapture` needs Screen Recording permission, which a terminal usually lacks. A synthesized key-down cannot enter a dead-key state, so dead keys need a real keyboard.

## Architecture

**ASDF systems.** `heml.base.asd` is the backend-independent core. Each backend is its own system that depends on it:
- `heml.tty`: terminfo/termcap terminal display (`tty-*.lisp`, `terminfo.lisp`, `linedit.lisp`)
- `heml.cocoa`: native macOS backend through the `objc` bridge (`cocoa-*.lisp`), SBCL only

`heml.tree-sitter` (highlighting, indentation and the language modes), `heml.lsp` (the language-server client) and `heml.term` (the terminal emulator) are systems of their own that the backends load.

`ioconnections.lisp` (the iolib event loop and connections) is the last module of `heml.base`. On SBCL it compiles at `(speed 2)`, from its own `declaim`. A forked child runs `%exec-in-child` inside a handler that ends it with `_exit` whatever fails: otherwise a failed `chdir` or terminal setting unwinds a copy of the editor's Lisp, which goes on running in the child. `connection-write` queues what is written, and a write handler is set exactly while the queue is not empty: it removes itself when it empties it. (A one-shot handler is removed only after the loop has handled every descriptor ready in that pass, so a filter that wrote in the same pass found the handler still set, failed, and left a queue nothing would ever write.)

All sources live flat in `src/`. Module membership and load order are defined only in the `.asd` files. When you add a file, register it in the right module. `core-2` is `:serial t`, so position matters there.

**Layers within `heml.base`.**
- `core-1`/`core-2`: the text model (`line`, `htext1-4`, `buffer`, `ring`), Heml variables (`vars`), the command interpreter (`interp`), `syntax`, search, and the redisplay model (`window`, `winimage`, `linimage`, `screen`, `display`, `cursor`). It also holds `connections.lisp` and `rompsite.lisp`, which are the event-loop and I/O abstractions.
- `wire`: an RPC layer (`wire`, `remote`, `port`) for talking to slave Lisps and eval servers.
- `root-2`: `main.lisp` (entry points and command-line parsing), `echo`, `streams`, `font`.
- `user-1`: all user-facing commands and modes, including file commands, Lisp mode, the REPL/eval server, spell, dired, bufed, shell and so on. `bindings.lisp` holds the default keymap and is loaded last.

**Packages** (`src/package.lisp`):
- `heml-internals` (nickname `hi`): the core.
- `heml-interface`: the public extension API, re-exported through `hi`.
- `heml`: commands and modes.
- `heml-ext`: portability shims.
- `heml.wire` (nickname `wire`), `heml.terminfo`, and `heml-user`, where user init code runs.

When you use a new internal symbol from another package, export it from `package.lisp`.

**Backend dispatch.** `call-with-editor` in `main.lisp` picks a backend keyword (`:tty`, `:cocoa`) and dispatches through generic functions specialized with `(eql :backend)`: `backend-init-raw-io`, `%init-screen-manager`, `make-event-loop`, `dispatch-events-with-backend`, and so on. Both share the iolib event loop. To see what a backend must provide, grep for `(eql :cocoa)`.

**Redisplay is never incremental.** Each redisplay rebuilds every visible window's image from its display start (`update-window-image` in `winimage.lisp` fills the dis-lines through `compute-line-image`). The device then draws all of it through its single `device-redisplay` method. Nothing records what changed, so nothing can be left stale. `compute-line-image` calls the buffer's mode's highlighter (`highlight-line`), which keeps syntax highlighting current on every line shown. The TTY device writes every row and clears each one to the end of the line, with no clear beforehand, so it doesn't flicker. Its output goes to the terminal's fd synchronously (`write-and-maybe-wait`), because redisplay often runs inside an event handler (for example, a shell's output) where dispatching events again isn't safe. Redisplay entry points return NIL when they have drawn: the input loop redisplays again while one returns true.

Each pass is bracketed by `device-begin-redisplay` and `device-end-redisplay` (`with-device-redisplay` in `display.lisp`). On the TTY these wrap the frame in synchronized output (DEC mode 2026, turned off by `*tty-synchronized-output*`) and hide the cursor while drawing. Where `civis` is DECTCEM, the cursor is shown again with DECTCEM alone, because `cnorm` can do more, such as xterm's turning off a blinking cursor. Redisplays caused by events are at most `*redisplay-interval*` (1/60 s) apart. The input loop waits out the rest of that interval for more events before it draws again, and ordinary stream output (`redisplay-windows-from-mark` with THROTTLEP) skips drawing within it. An explicit `finish-output` or `force-output` still draws at once. So does output within `*echo-interval*` (1/10 s) of the last key read (`*last-key-time*`, `echo-expected-p`, `input.lisp`), which is most likely the key's echo: held for the interval, a terminal's echo was drawn about 20 ms after the key, and is now about 1.5 ms after it in the terminal and 3 ms in Cocoa; a terminal reads its screen at once then too (`term-note-output`). When idle, the loop waits for input only until the next event `schedule-event` queued is due (`next-scheduled-event-wait`, exact rather than rounded, so that it never polls), so scheduled events run on time rather than at the next keystroke.

The backend keyword is also mapped to a connection backend in two `ecase` forms: `%call-with-editor` in `main.lisp` and `%start-slave` in `eval-server.lisp`. A new backend must be added to both.

**Syntax highlighting** belongs to a buffer's major mode. `define-mode-highlighter` (`exp-syntax.lisp`) names a function of a line that brings its font marks up to date, and `compute-line-image` calls it, through `highlight-line`, for each line it draws; its `:marks` names the line property in which the function keeps `(key . font-marks)` (every highlighter does: `tree-sitter`, `grep-marks`, `dired-marks` and so on), and `forget-highlighting`, on "Buffer Major Mode Hook" and when a mode's highlighter changes, deletes those and Lisp's tags' marks, so that a buffer that changes mode keeps none of the old mode's colours (it did, and they hid its links). A mode that names none is not coloured but for its links (`highlight-links`), on lines with no colours of their own: a selection's marks (`*region-font-marks*`) are not the line's (a line drawn while selected kept no links). A highlighter keeps only its own marks: one that deleted every font mark on a line took a selection's too (the Debugger buffer's did). A killed buffer's tree-sitter parse is freed (`forget-parse`, on "Delete Buffer Hook"), and a query's `#match?` and `#lua-match?` patterns are compiled once (`predicate-scanner`). `heml.base` gives Lisp mode `line-tag`, the hand-written Lisp parser in `exp-syntax.lisp`. Tags are also computed for their package, which the modeline shows in every buffer, so `recompute-syntax-marks` makes marks only where `lisp-highlighted-p`. `heml.tree-sitter` (`tree-sitter.lisp`, `tree-sitter-modes.lisp`; SBCL and ECL, loaded by the TTY and Cocoa systems) highlights with tree-sitter. Its interface passes a 32-byte node struct by value, which CFFI cannot, so the `ts` macro calls a function through `sb-alien` on SBCL and through a function pointer in `ffi:c-inline` on ECL; memory is CFFI's, and libraries are loaded with `sb-alien:load-shared-object :dont-save t` on SBCL, since CFFI's loader there runs on the initial thread, which Cocoa's main loop holds. `define-tree-sitter-language` ties a grammar to a mode: C, Markdown, Python, Shell Script (Bash's grammar), Rust, Go, JavaScript, TS (TypeScript: "Typescript" is Hemlock's name for a slave's transcript, and mode names ignore case), TSX, JSON and YAML are modes of their own (the last seven from `define-brace-language` and its like in `tree-sitter-modes.lisp`), Pascal mode (Hemlock's) is coloured by Pascal's grammar, and Lisp mode uses tree-sitter's Common Lisp grammar with `line-tag` as its `:fallback`: the first time the grammar is needed and cannot be loaded, the mode goes back to `line-tag` for good. `line-tag` colours strings, comments (`#| |#` too), keywords, a `#+`/`#-` feature expression (not the form after it), and the name a top-level definition defines (`definition-name-bounds`: an operator in `*definers*`, `define-...`, or a macro named `def...` this Lisp has, and not on a line that starts inside a string); it reads `|symbol|` and `a\"b` as symbols (a `"` in one started a string to the end of the file); and a line's `(in-package ...)` -- `:foo`, `#:foo`, `"FOO"` or `foo`, in any case, the first line's too -- names the package (`line-package`). `define-mode-highlighter` resets every buffer's tag line so that tags computed under the other highlighter are computed again. Why a language could not be loaded is kept in its `problem` slot, never printed: the terminal editor's error output is its screen. A buffer is parsed again when its `buffer-signature` changes, incrementally: `changed-octets` finds the lines that changed since the last parse as the language-server sync does (a line whose characters are the same string object is unchanged), encodes only those as UTF-8 into the last parse's octets, updates the row table (`parse-line-starts` is a line's row, `parse-row-starts` a row's byte), and tells the old tree that one span (`ts_tree_edit`), and the parse reuses it -- so an edit costs about the same in a file of ten megabytes as in a small one; `buffer-octets` makes it all from nothing for a first parse; and a line is coloured from the highlight query's captures within its bytes; `*capture-fonts*` maps capture names to colours, by their leading components, most specific first (`@string.escape` is an escape, not a string), and a language's `:precedence` says whether the first or the last of two patterns on the same text wins (tree-sitter's queries and Neovim's differ). With `:indent`, a language also indents its mode's lines (`tree-sitter-indent-line`, the mode's "Indent Function", with spaces): `indent-column` follows Neovim's algorithm over the language's `indents.scm` (`@indent.begin`, `.branch`, `.end`, `.dedent`, `.align`, `.auto`, `.ignore`, `.zero`, and `#set!` settings), from the node the line starts with, or for a blank line the one the line before ends with. Code being typed parses as errors, so inside an ERROR, and on a blank line after one that `:finishes` a block (Python's `return`), `textual-indent` works from the line before instead: a level more if it `:opens` a block, less if this line `:closes` one, from the line its statement began on (`statement-start`, by parentheses). In Lisp mode Return is "Lisp Return" (`lispmode.lisp`), which indents the new line as `C-j` does while "Lisp Indent on Return" (a Lisp-mode variable, true by default) is, and starts it at the margin when it is NIL (see Lisp editing for the rules). Return is "New Line and Indent" in C, Python, Shell Script and Pascal, which indents the line it leaves too, and `}` indents in C. Neovim's queries serve C, Pascal, Python, Rust, Go, the JavaScript family (whose queries inherit from each other, so the script concatenates `ecma`, `jsx` and the language's own), JSON and YAML; Bash's is Heml's own (`scripts/tree-sitter-queries/bash/indents.scm`). A language's `:opens-always` (YAML) indents a new line after one that `:opens` a block whatever the tree says, since there indentation is the block. Go is indented with tabs. The library, grammars and queries are found at run time in `*tree-sitter-directories*`, each laid out as Homebrew lays them out; without them a buffer is simply not coloured. Markdown is two grammars: the block grammar leaves the text of headings, lists and paragraphs in `(inline)` nodes, which `parse-inline` parses again with the inline grammar (the language's `:inline`), limited to those ranges with `ts_parser_set_included_ranges`; `line-fonts` lays down the block query's spans and then the inline query's, and `merge-fonts` lets an inner style add to an outer one (`***both***` is bold and italic). A fenced code block that names its language is coloured as that language (the language's `:code-blocks`): `parse-code-blocks` finds the blocks and their names with a query, maps a name to a grammar through `*code-block-languages*` (`py`, `sh`, `js`, `lisp` and the like), and parses all of one language's blocks together with `parse-ranges`, into the parse's `injections`; on a line of a block `line-fonts` clears what the block grammar made of it and lays down that language's spans. A block in a language Heml has no grammar for stays as code. `make tree-sitter` builds the C, Markdown (block and inline), Pascal, Bash, Common Lisp, Rust, Go, JavaScript, TypeScript, TSX, JSON and YAML grammars into `build/tree-sitter/` (TypeScript's highlight query is its own followed by JavaScript's) (`scripts/tree-sitter-grammars.sh`, pinned tags); the library and Python's grammar come from Homebrew (`brew install tree-sitter tree-sitter-python`). `make install-tree-sitter` copies the grammars to `$XDG_DATA_HOME/heml/tree-sitter/` (`~/.local/share/heml/tree-sitter/`, `TREE_SITTER_DIR`), where the installed app finds them.

A language's `:definitions` are the node types (C's `function_definition`, Python's classes too, Pascal's `defProc`) that `definition-spans` finds by walking the tree: `C-M-a`, `C-M-e` and `C-M-h` ("Beginning of Definition" and its fellows) move by them in those modes, and "Outline" lists them, or a Markdown buffer's headings, in the result buffer `*Outline*`. `tree-sitter-modes.lisp` also holds each language mode's commands and menu: "Find Other File" (C's header or source, `C-c o`), "Shift Region Right"/"Left" (Python, `C-c >`/`C-c <`), "Python Run File", "Shell Script Run File" and "Pascal Compile File" (`C-c C-c`, into the compilation buffer; Pascal's grammar knows Delphi's and Free Pascal's dialects, and `fpc`'s `x.pas(3,5) Error:` lines are places), "Send Region to Shell" (`C-c C-r`), Markdown's heading commands (`C-c C-n`, `C-c C-p`, `C-c =` and `C-c -`), and "Markdown Fill Paragraph" (`M-q`), which hangs a list item's lines under its text and keeps a quotation's `>`. Rust, Go, JavaScript, TS and TSX run the program with `C-c C-c` ("Rust Run": `cargo run` at the nearest `Cargo.toml`, `--bin` or `--example` for such a file; "Go Run": `go run .`; "JavaScript Run": `node FILE`, which strips TypeScript's types), all the tests with `C-c t f` ("Rust Test", "Go Test", "JavaScript Test": `npm test` under a `package.json`, else `node --test FILE`), the test point is in with `C-c t t` (its name found by looking back with `*test-at-point-scanners*`: `cargo test NAME`, `go test -run '^NAME$'`, `npm test -- -t NAME` or `node --test --test-name-pattern`), and the last tests again with `C-c t a` ("Test Again", `*last-test*`), each into the compilation buffer through `run-in-compilation`, which shows it in the other window and stays in this one (as Python's, Shell Script's and Pascal's commands now do too), and with an argument offers the command to change first; `directory-above` finds the directory a tool works from. The Compilation buffer reads rustc's `--> x.rs:3:5`, a Rust test's `panicked at x.rs:3:5`, a Go test's indented `x_test.go:12:`, tsc's `x.ts(3,5): error`, Node's `test at x.js:3:1` and its stack frames (`*other-location-scanners*`, `grep.lisp`, whose third group is the column). A language's `:single` names a line that governs one statement (Pascal's `then`, `do` and `else`): after that statement, `textual-indent` goes back to the governing line's indentation.

**Lisp editing** (`lisp-sexp.lisp`) is sexp-edit's (`vendor/sexp-edit`, lispnik/sexp-edit, a submodule `heml.base.asd` pushes onto the central registry unless a `sexp-edit` is already registered, as it is when the Lisp Listener's application loads Heml): the structural editing and indentation the Lisp Listener's REPL and its iOS editor use, so that a key does the same thing in all three. Its commands are pure, `(text offset)` to `(values text offset)` or NIL to decline; `run-sexp-command` gives one the text around point (`sexp-window-start`: the outermost open parenthesis around point by Lisp mode's parse, with a quote before it, or at top level the top-level form before point, never before the parse block nor a REPL buffer's input; `sexp-window-end`: past that form and the form after point), and makes the answer as one deletion and one insertion of what differs (`replace-sexp-text`), so marks and undo see an ordinary edit. In Lisp mode, while "Lisp Structural Editing" is true, `(` and `"` put in pairs ("Lisp Insert (", "Lisp Insert \""), `)` steps over the closing one ("Lisp Insert )", which otherwise inserts and shows the match), and "Wrap Form" (`M-(`), "Splice Form" (`C-c M-s`), "Raise Form" (`C-c M-r`), "Slurp Forward" (`C-)`, `C-c )`), "Barf Forward" (`C-}`, `C-c }`), "Slurp Backward" (`C-(`, `C-c (`) and "Barf Backward" (`C-{`, `C-c {`) work; Heml's keys stay where the Listener's clash (`C-k`, `C-M-k`, `M-s`, `M-r`, and its own `C-M-f`, `C-M-b`, `C-M-t`); with "Lisp Keep Parens Balanced", Backspace after a matched `)` and Delete (`C-d`, and in `heml:repl` "Linedit Delete Or Eof") before a matched `(` move inside, an empty pair or string goes whole, and an unmatched paren is deleted. Each calls Self Insert Hook as a typed character does. Lisp mode's "Indent Function" (`indent-for-lisp`, so Tab, `C-j`, Return and `C-M-q`) is `sexp-edit:indentation-at` on the text from the window's start, with the start's column, "Spaces per Tab", "Lisp Indentation Local Definers" and the buffer's package bound: a body two in, a body form's distinguished arguments four in, a call under its first argument, a line under the previous element that begins one, LOOP's clauses under the first, `flet`'s functions like a `defun`, `'(...)` and `#(...)` as data, `&body` from the live macro's lambda list; `lisp-indent-region` (`C-M-q`) leaves a line that begins inside a string alone. `defindent` adds to sexp-edit's table, which holds Common Lisp's forms; Heml's own are defined in `lisp-sexp.lisp`. sexp-edit's corpus of edits, `sexp-edit-tests:*edit-cases*`, is replayed through `run-sexp-command` in a Lisp buffer by `sexp-corpus-failures`, which both smoke tests call (loading the corpus, `tests/cases.lisp`, as source: compiling in the terminal editor writes on its screen); the Listener replays it on a text view. Change the editing in sexp-edit, and test it there (`make test`, `make test-ecl`).

**Result lists** (`results.lisp`): a buffer listing places, one a line, has the buffer variable "Result Location Function", a function of a line that returns `(pathname line column)` or `(pathname :position n)`, or NIL for a header; `plist-line-location` reads a place kept in the line's plist, for lists that never change. In every result mode Return visits the place in the other window, `n` and `p` show the next and previous, `C-o` shows it, and `q` buries the list; ``C-x ` `` ("Next Result") visits the next place of the list made last, `*result-buffer*`, from anywhere. Grep, Compilation, Xref and Outline are result modes. Grep and Compile (`grep.lisp`) run a command ("Recursive Grep" asks only for a pattern and a directory, and uses `rg` when it is installed) with its own filter and sentinel, writing to the end of the buffer, never at point; the sentinel writes the count, and must not redisplay (no `message`), since it runs inside an event handler. A line `file:line:[column:]` names a place; Compilation also reads Python's `File "x", line N` and a shell's `x: line N:`. Grep colours the file, line number and what matched, from the pattern `grep-pattern-scanner` reads out of the command. `C-x C-q` makes a Grep buffer Wgrep, where `C-c C-c` writes each changed line to its file's buffer (it checks the line there is still what grep found) and `C-c C-k` puts them back. Setting `(current-window)` does not change the current buffer: go to a window with `select-window`, or `change-to-buffer` after it.

The other list modes build their lines from state and keep each line's entry in its plist, with a highlighter of their own: Apropos (every kind a symbol names, space describes, `.` visits), Debug (a frame's locals and source are gathered while the slave is in the debugger; Return shows the locals, `.` the source), Slave-List (a header and each slave's state), and Completelist and Fuzzylist (what the completions share, the next character, and a fuzzy match's characters).

**Projects** (`project.lisp`): a file's project is the nearest directory above it holding one of `*project-markers*` (`.git`, `.hg` and the like), or else the nearest holding one of `*project-build-markers*` (`Makefile`, an `.asd`, `package.json` and the like); `project-root` caches the answer by directory, and the home directory and `/` are never roots. `project-files` asks `git ls-files`, then `rg --files`, then walks the tree. `C-x p` holds the commands, as in Emacs ("Previous Window" moved to `C-x O`): `f` finds a file (completion over the project's files; text that is no file's name finds those with its characters in order, ranked by `fuzzy-file-score`, and lists several in `*Project Files*`, the best first), `g` greps and `c` compiles at the root (the last command kept per project), `s` a shell there, `!` a shell command, `d` Dired, `p` switches project, `b` a project buffer, `l` Bufed filtered to the root (a Bufed filter starting with `/` is a directory), `r` replaces a string in every file that has it ("Project Replace": the files from `rg -l -F`, the count asked about, the edits made in the files' buffers, the changed lines listed in `*Project Replace*`, then the buffers saved if wanted), `k` kills the project's buffers, `F` forgets it, `e` edits its settings. A file `.heml-project` at the root, a property list read as data (`project-settings`, read again when the file changes), also makes its directory a root: `:name` is what the modeline shows, `:compile` what `C-x p c` offers at first, `:ignore` the files `C-x p f` leaves out (`dir/`, `*.ext` or a path's start), `:settings` its language servers' settings (see Language servers), and `:variables` an alist of Heml variable names and values set in each of the project's file buffers. Projects become known through "Buffer Pathname Hook" and are kept, with each project's session, in `*project-state-directory*` (`$XDG_STATE_HOME/heml/`, or `HEML_STATE_DIRECTORY`; the tests set it; what an older Heml kept in `~/.heml/` is moved there the first time). A session is the project's files, their points, and the window layout as `device-layout`'s tree, whose windows show a file, one of the project's directories in Dired, or its shell; it is saved on leaving a project with `C-x p p` and on exit ("Exit Hook"), and restored on switching to it and, through "Entry Hook", on starting with no files in a project. "Project Sessions" turns that off. A session also holds what was typed to the project's shell (`:shell-history`, put back in the shell's "Interactive History" when `project-shell` starts it), and the project's compile commands are kept in its entry in `projects.lisp` (`:compile-history`): `C-x p c` binds `*echo-area-history*` to them, so `M-p` at its prompt goes back through them. `recent-files.lisp` in the same directory lists the files visited, the latest first (`note-recent-file`, on "Buffer Pathname Hook"); `C-x C-r` is "Find Recent File", with the same fuzzy matching as `C-x p f` ("Insert File" is `C-x i`, as in Emacs). The modeline's `:project` field, after the modes, shows `[name]`.

**Completion at point** (`popup.lisp`): "Complete at Point" (`C-M-i`, and Tab in a word through "Indent Or Complete" and "Completion Function") asks the mode's "Completions Function" for the completions of what is before point and where it starts -- Lisp's symbols from the slave (`eval-form-in-server-1`) or the editor's image, and the buffers' tokens (each with its kind as a note: a completion is a string or `(string . note)`); in a shell buffer file names, from the shell's directory; elsewhere the buffers' words -- and `popup-choose` shows them in a popup under point, reading keys itself as incremental search does: `C-n`/`C-p` or the arrows choose, Return or Tab puts the choice in, typing narrows, anything else is put back and ends it. At a file prompt, Tab on an ambiguous name shows the files in a popup at the foot of the window above (`choose-file-completion`, `bottom-window`). "Complete as You Type" (a variable and a command) brings the popup up by itself, through "Self Insert Hook", once a word is "Complete as You Type Length" long; then only Tab puts a choice in. **Signatures** (`popup.lisp`): with "Signature Help" on, typing `(` or `,` (in Lisp, a space after the operator) calls the mode's "Signature Function", which shows what the call takes with `show-signature`: a one-row popup over the call's opening parenthesis that, unlike the others, stays while one types. "After Command Hook" (`update-signature`) moves it with the text and takes it away when point leaves the call's line or goes before it; `)` and C-g take it away too. Lisp's is the operator's arglist, from the slave or `conium:arglist` here (`%arglist-string`); a served mode's is the server's `signatureHelp`, asked without waiting, whose answer is dropped if `*signature-tick*` has moved on, and whose active parameter is marked through the popup's `highlights`. The popup is device-independent: `*popup*` (`winimage.lisp`) is rows of text and a font each, with `highlights` for parts of a row in another font, and `update-window-image` lays them over the window's dis-lines (`overlay-popup`, `linimage.lisp`), adding dis-lines past the buffer's end (whose `dis-line-line` is NIL) when it needs them.

**Language servers** (the system `heml.lsp`): a client for the Language Server Protocol, in six files loaded in order (`:serial t`): `lsp.lisp` (JSON, the `lsp-server` and `document` structures -- defined before anything sets their slots, which ECL needs -- settings, messages, positions), `lsp-server.lisp` (what a server asks and says, watched files, starting and stopping), `lsp-sync.lisp` (keeping each server's copy of a buffer, `lsp-idle`, `lsp-current-server`), `lsp-diagnostics.lisp`, `lsp-commands.lisp` (going places, describing, actions, rename, formatting, outline, signatures, completion) and `lsp-features.lisp` (calls, highlighting, colours, hints, lenses, folds), which ends with `define-language-server` and the servers Heml knows, so that every command a mode is given is defined by then. `define-language-server` names, for a major mode, the commands that run a server and the protocol's language id: the first whose program `find-program` finds is run, and one that dies before it is ready, or refuses `initialize`, gives way to the next (`lsp-server-died`); when none starts, the group and root go into `*lsp-failures*` and nothing is tried there again until "LSP Restart"; a server that dies by itself once it is ready is started again, but one that does so three times in a minute (`note-lsp-crash`) goes into `*lsp-failures*` too, and the modeline then says `(no server)`. A mode's `:group` names the modes that have one server between them in a project: JavaScript, TS and TSX are "TypeScript", and each buffer is opened with its own mode's language id. C has `clangd`, Python `pyright-langserver`, `pylsp` and others, Shell Script `bash-language-server`, Pascal `pasls`, Rust `rust-analyzer`, Go `gopls`, JavaScript, TS and TSX `typescript-language-server` and then `tsc --lsp --stdio` (TypeScript 7's compiler is a server, and typescript-language-server cannot use a TypeScript that new, which is what Homebrew pairs it with), JSON `vscode-json-language-server`, YAML `yaml-language-server`. A server is one process for a group and a project's root (`buffer-language-server`), started by `lsp-idle`, a scheduled event twice a second, for the current buffer, when "Language Servers" is true (`lsp-idle` also syncs every other buffer the servers know); it is a process connection whose filter (`lsp-receive`) collects bytes into messages by their `Content-Length` and whose error output is discarded. JSON is jzon's: objects are hash tables with string keys (`json`, `jref`), arrays vectors, false NIL, null the symbol `NULL`. The buffer's text is sent on opening, and when `buffer-signature` has changed its change is (`lsp-sync`, before every request and from `lsp-idle`): to a server whose `textDocumentSync` is incremental, the lines that changed (`line-change`): the `document` keeps the buffer's lines and their strings as last told, and since a line's characters are a new string whenever they change (the open line's a number that changes), going through the lines from each end while they are the same object finds the change without copying or comparing text; to another server, the whole text. (`text-change`, which compares two strings, is what the Cocoa test checks the protocol's arithmetic with.) A request (`lsp-request`) waits for its answer in `lsp-wait`, dispatching events, and gives up after its timeout; positions are lines from 0 and UTF-16 code units (`lsp-position`, `lsp-move-mark`). A server with a `diagnosticProvider` is asked what is wrong (`lsp-pull-diagnostics`, `textDocument/diagnostic`, after a buffer is opened or changed, about its other buffers too when it has `interFileDependencies`, and again when the server sends `workspace/diagnostic/refresh` or was too busy to answer); what a server says and what it answers are kept apart, in its `pushed` and `pulled` tables, since some do both for different things (rust-analyzer), and what is wrong with a file is both. `publishDiagnostics` becomes marks in `*buffer-diagnostics*` and is drawn through `hi:*line-decoration-functions*`: a function of a line returning `(start end font)` lists, which tree-sitter's `line-fonts` lays over its colours, drawing the line again when `hi:*decoration-tick*` has changed. In a served mode `M-.` is "LSP Find Definition", `M-?` "LSP Find References" (a result list), `C-c C-d` "LSP Describe" (the error on the line and the hover text, in `show-text-popup`, a popup until the next key), and the mode's "Completions Function" is `lsp-completions`, the server's items with their kinds for the completion popup, or the buffers' words when it has none; `C-c C-a` is "LSP Code Action": the server's fixes and refactorings for what is wrong at point, chosen from `popup-select` (a popup menu: `C-n`/`C-p`, a digit, Return), and done by making the action's edit (`apply-workspace-edit`) or by `workspace/executeCommand`, whose edits the server asks for with `workspace/applyEdit`, answered in `lsp-dispatch`. "Outline" asks `*outline-functions*` first, where `lsp-outline-entries` gives the server's `documentSymbol`s with their kinds. `M-n` and `M-p` go to the next and previous error and say what it is; `C-c C-s` ("LSP Find Symbol") lists the project's symbols matching some text (`workspace/symbol`); the modeline's `:lsp` field, after the project, counts the buffer's errors and warnings, updated as they arrive (`update-lsp-modeline`); and with "LSP Format on Save" a buffer is formatted by its server on "Before Write File Hook". "LSP Rename", "LSP Format Buffer", "LSP Diagnostics" and "LSP Restart" are commands and items of the mode's menu. In Lisp mode the same keys are the slave's: `M-.` "Find Definitions", `M-?` "Who Calls", `C-c C-d` "Describe Symbol". A server's settings are JSON written in Lisp (`lisp-json`: an object is an alist with string keys, an array a vector or a list that is no alist, `:true`, `:false` and `:null` themselves): `*language-server-settings*`, under the `:settings` of the project's `.heml-project` (`language-server-settings`, merged member by member). They answer `workspace/configuration` by section, a dotted path (`settings-section`), and are sent with `workspace/didChangeConfiguration` once the server is initialized, when there are any; `(:settings (("yaml" ("schemas" ("file:///x/schema.json" . "*.yaml")))))` gives the YAML server a schema. More of the protocol, each checked against `test/fake-lsp.py` and, where a real server shows it in text, by `make smoke-lsp`:
- *Each server of a buffer* that is ready is given to the `*lsp-idle-functions*`; highlighting, colours, hints and lenses each come from the first of the buffer's servers that gives them (`buffer-server-with`).
- *Several servers for a buffer.* `define-additional-language-server` gives a mode's buffers another server beside the mode's own, known by a name that is its group (Python has `ruff server`). `buffer-language-servers` is all of them, the mode's own first, and `buffer-language-server` that one; `rebuild-buffer-diagnostics` makes a buffer's diagnostics from what every running server says of its file (each entry ends with its server); "LSP Code Action" asks each server about what it found; `C-c C-d` says what each says, and the completions are those of all of them; and `lsp-current-server` with a capability's name gives the first server that has it, which is how formatting goes to ruff and how each command goes to a server that can do it.
- *Positions.* `*encoding*` is what a character counts for the server being talked to: `:utf-32` (characters), which Heml asks for first, or `:utf-16`. `lsp-current-server` sets it for the command under way; `lsp-dispatch`, `lsp-sync` and anything else that talks to a server outside a command bind it. `unit-offset` and `unit-charpos` convert.
- *What a server asks and says* (`lsp-answer`, `lsp-told`): `client/registerCapability` for watched files; a `window/showMessageRequest` with choices is kept in `*lsp-questions*` and answered `:later`: `queue-command` has the command loop call `lsp-ask-question`, which shows the choices in `popup-select` and sends the answer; `window/showMessage` and `logMessage` go to `*lsp-said*`, which `lsp-idle` puts in the buffer "Language Servers", showing errors, warnings and information in the echo area (nothing may be drawn while a message is being handled); `$/progress` is kept in the server's `progress` and shown in the modeline, `(Indexing 40%)`.
- *Watched files* (`lsp-look-at-files`): every `*lsp-watch-ticks*` half seconds the project's files (`project-files` with `:fresh t`, since a walk of the tree is otherwise kept for half a minute; so not what git ignores) that match a server's registered globs (`glob-scanner`) are compared by write date with the last look, and the server is sent `workspace/didChangeWatchedFiles`. Settings are sent again when `.heml-project`'s date changes (`lsp-send-changed-settings`).
- *Requests given up on* are cancelled (`$/cancelRequest`). "LSP Rename" asks `prepareRename` first. A code action with no edit is resolved (`codeAction/resolve`). A workspace edit may make, rename and delete files (`apply-file-operation`).
- *Going places:* "LSP Find Declaration", "LSP Find Type Definition" (`C-c C-t`), "LSP Find Implementation" (`lsp-go-to`); "LSP Incoming Calls" (`C-c C-u`: a terminal's `C-h` is its Backspace) and "LSP Outgoing Calls", result lists.
- *Formatting:* "LSP Format Region"; with "LSP Format on Type", after a command that changed the buffer and left one of the server's trigger characters before point, `onTypeFormatting` is asked without waiting and its edits made if nothing more was typed.
- *Completion:* `lsp-completions` keeps the server's items by the text each is known by (`*lsp-completion-items*`); the mode's "Completion Accept Function", `lsp-accept-completion`, resolves the item, makes its `additionalTextEdits` (the import it needs), and puts in its text, as a snippet when it is one; "Completion Describe Function" gives its documentation for `C-h` or `M-h` in the popup.
- *Around point and over the text*, from `*lsp-idle-functions*` (called with the current buffer's own server twice a second): `lsp-highlight-uses` asks for the other uses of the name point rests on ("LSP Highlight Symbol") and shows them bold and underlined; `lsp-refresh-extras` asks, when the buffer has changed since (`document-extras`), for semantic tokens ("LSP Semantic Highlighting", on: `*token-fonts*` maps a few kinds -- types, functions, macros, namespaces, parameters -- to fonts laid over the grammar's colours, kept by line in `*buffer-tokens*`), inlay hints ("LSP Inlay Hints", on, a command toggles it: shown where they would be written, a type after its name and a parameter's name before its argument, through `hi:*line-inline-functions*`; each is kept at a mark, so that it stays with its text as the line is typed in) and code lenses ("LSP Code Lenses", off; "LSP Code Lens", `C-c C-l`, does one: a server's own command through `workspace/executeCommand`, showing references itself, and saying so of anything only an editor could do; rust-analyzer's Run, `rust-analyzer.runSingle`, is run as a compilation, `cargo` with the runnable's arguments, and its `gotoLocation` goes there -- the client tells a server which of these it does, in its `experimental.commands` capability, and rust-analyzer offers Run only then). A server that was busy, or that the text overtook, is asked again the next time round, and a buffer of more lines than "LSP Extras Line Limit" (200,000; NIL for none) is not asked about at all.
- *Folding:* the mode's "Fold Ranges Function" is `lsp-fold-ranges`.

`HEML_LSP_LOG` names a file every message is added to, and what went wrong sending or reading one (lines starting `!!`). jzon comes from `vendor/jzon`, a submodule of Zulu-Inuoe/jzon that `heml.lsp.asd` pushes onto `asdf:*central-registry*`: the jzon ocicl has (20251113-f05afbb) does not compile under ECL (its `native-namestring` uses UIOP's `os-cond`, `os-unix-p` and `unix-namestring` unqualified on Lisps other than SBCL, CCL and CMUCL), and jzon's fix, 703cb7e, is later. When ocicl has a jzon with it, the submodule can go and `com.inuoe.jzon` go back into `ocicl.csv`. Both backends load `heml.lsp`, on SBCL and ECL. The servers themselves are run by `make smoke-lsp`: `clangd`, basedpyright, `bash-language-server` (whose errors are ShellCheck's), `rust-analyzer`, `gopls`, TypeScript's, and the JSON and YAML servers; `pasls` has never been run, having no package. `test/fake-lsp.py` is the server the smoke tests check the client against, and with an argument another kind of server (`--refuse` will not start, `--crash` dies when a file is opened, `--pull` says what is wrong only when asked); it asks for the setting `fake.greeting` and shows it in its hover: `test/smoke.lisp` in Cocoa, and `test/smoke-tty.sh` in the terminal under SBCL and ECL, each naming it as Pascal's server for the run. Both clear every mode's commands first, so that no server the machine has is started in them: only `make smoke-lsp` runs real ones.

**Folding** (`fold.lisp`): "Toggle Fold" (`C-c C-f`) hides what starts on point's line, or else what the line is in, under its first line, and on a line with a fold under it opens it; a line after the fold that holds only what closes it (a brace, with a semicolon) is folded with it, and the header then reads `{  ... 13 lines }`; "Fold All" folds everything not within something else, "Unfold All" opens all. What can be folded is the mode's "Fold Ranges Function" (a language server's `foldingRange`) or else each line with the more indented lines after it (`indentation-fold-ranges`). A hidden line has `hi::hidden` in its plist and nothing else knows: `update-window-image` goes from the line before a fold to the next shown (`next-shown-line`), and the header line says `... N lines` after its end. `keep-point-shown`, on "After Command Hook", takes point across a fold when it came from the line next to it (C-n, C-p) and otherwise opens the fold (a search found something in it).

**Git** (`git.lisp`): everything asks the `git` program, run in the repository (`git`, which turns off the user's colours, quoting of file names and diff prefixes; `git-ok`, which makes a failure an editor error saying what git said), and waits, but for pushing and pulling (`run-git-process`, into `*git output*`). A Git buffer's lines keep what they are about in their plist (`git-entry`, a property list after a kind: `(:file f :section s)`, `(:hunk lines :header lines :offset n ...)`, `(:commit hash)`, `(:section s)`, `(:header t)`) and their colours (`git-fonts`, or `git-diff` for a diff's line, coloured by `diff-line-fonts`), put there by `fill-git-buffer`; the buffer's repository is its "Git Root". `C-x g` is "Git Status" ("Get Register" moved to `C-x r i`, "Put Register" to `C-x r s` too, as in Emacs): the head, upstream and counts, then the untracked, unstaged and staged files (`git status --porcelain=v1 -z --untracked-files=all`) and the latest commits; Tab shows a file's hunks (`*git-expanded*`), `s` stages a file, a hunk (`git apply --cached` of the file's diff header and that hunk) or a section's files, `u` unstages (`git restore --staged`, or `git rm --cached` before the first commit), `k` discards after asking (`git restore`, a hunk `git apply --reverse`, an untracked file deleted) and reads changed buffers again, `S`/`U` stage or unstage everything, `c` commits (an argument amends), Return visits a file, a hunk's line or a commit, `d` shows a diff, `l` the log, `g` makes it again, `P` pushes, `F` pulls. Every change calls `git-changed`, which refills the repository's status buffers and drops its files' committed text. Committing writes the message in `*git commit*` ("Git Commit" mode, writable, `#` lines left out by `--cleanup=strip`): `C-c C-c` commits, `C-c C-k` gives up; "Git Commit" (`C-x v v`) stages the buffer's file first when nothing is staged. Diff mode (`*git diff*`, `show-diff`, in the other window) is a result buffer whose "Result Location Function", `diff-line-location`, counts from the hunk's `@@` to the line in the file as it is now (on the `@@` line itself, the hunk's first line); `n`/`p` go by hunks. "Git Diff File" (`C-x v =`, saving first), "Git Diff" (`C-x v D`), "Git Log File" (`C-x v l`) and "Git Log" (`C-x v L`, the last `*git-log-limit*` commits), "Git Blame" (`C-x v g`, from `git blame --line-porcelain`, point on the line it was on), "Git Pull" (`C-x v +`) and "Git Push" (`C-x v P`); Return in a log or blame shows the commit ("Git Show Commit"), and there is a Git menu after Project. **The fringe's marks**: a buffer of a file Git tracks (`git ls-files --error-unmatch`, through "Buffer Pathname Hook", `note-git-buffer`) has a `git-file` in `*git-files*` and a fringe a column wider (`buffer-fringe-extra`, `winimage.lisp`; the marks are in its last column, after a debugger's); once a second (`git-idle`, a scheduled event), each buffer shown whose `buffer-signature` changed is compared with the file as last committed (`git show HEAD:./name`, kept until the repository's index changes date: `git rev-parse --git-path index`, since in a worktree or a submodule `.git` is a file) by `diff -U0` of the two written to temporary files (the buffer's lines joined by newlines, since a file ending in one is a buffer whose last line is empty), and `diff-line-kinds` turns the hunks into marks by line: a green bar beside lines added, a blue one beside lines changed, a red edge below a line after which lines were taken out (`*git-mark-fonts*`). "Git Fringe" turns it off; a buffer of more than `*git-fringe-line-limit*` lines is not compared.

**Annotations.** `hi:*line-annotation-functions*` (`winimage.lisp`) are functions of a line returning NIL or `(text . font)`, shown two columns after the line's end as far as the window is wide (`annotate-dis-line`, over the dis-line as a popup is): a fold's count, a server's lenses. A dis-line's `text-length` is its length before them, which is where the cursor goes at the end of the line.

**Text among a line's characters.** `hi:*line-inline-functions*` (`linimage.lisp`) are functions of a line returning `((charpos text font) ...)`: text shown before the character at `charpos`, as a server's hints are. Where a character is on the screen is worked out twice, by the image (`compute-line-image`) and by the arithmetic for the cursor, a click, wrapping and columns (`real-line-length` and `cached-real-line-length` in `cursor.lisp`, which everything else there calls), and the two must agree. For a line with such text both come from `flatten-inline-line`, which gives the characters the line shows and, for each of the line's characters, how far along it starts (before any text shown at it, so the cursor at a hint's place is before the hint): `compute-inline-line-image` cuts that into rows, handing the whole string from row to row as the rest of a character's representation is handed for other lines (`*inline-layout*` keeps its map), and `inline-line-length` is its length. Other lines go the old, fast way. A column (`mark-column`, `C-n`'s goal) counts such text.

**Snippets** (`popup.lisp`): `insert-snippet` puts in text with places to fill (`$1`, `${1:text}`, `${1|a,b|}`, `$0`; `parse-snippet`), marks them, and leaves point at the first; a number that comes again is a mirror of its place, made to hold what the place holds after each command (`mirror-snippet-place`), and `$NAME` or `${NAME:text}` is what `snippet-variable` says (the file's name, the line, the date) or else the text; Tab ("Indent Or Complete" asks `snippet-next-place` first) goes to the next, a character typed at an untouched place replaces its text ("Self Insert Hook"), and the snippet is over at `$0` or when point leaves it. `*snippet*` holds the one being filled in.

**The fringe** (`winimage.lisp`), as in Emacs: columns at a window's left, beside its text and not in it, for what is said of each line. A window has one as wide as its buffer's major mode's `mode-fringe-width` (0 by default) and its buffer's own `buffer-fringe-extra` beyond that (`buffer-fringe-width`; Git's column), or `*fringe-width*` when that is set; `window-fringe-width` says how wide, and `window-text-width` how many columns are left for the text. `update-window-image` lays a line out in the text's width, records `dis-line-text-length`, and then `fringe-dis-line` moves the image and its font changes right by the fringe and draws there what the functions in `hi:*line-fringe-functions*` (a line to `((column text font) ...)`) return, beside the line's first row. The cursor arithmetic in `cursor.lisp` works in text columns: `mark-to-cursorpos` adds the fringe to its x, `cursorpos-to-mark` takes it away (a click in the fringe is the text's first column), and centring and scrolling use `window-text-width`. Annotations after a line's end count the fringe in.

**Debugging** (`dap.lisp`, in the system `heml.lsp`): a client for the Debug Adapter Protocol. `define-debug-adapter` names, for modes, the commands that run an adapter, a function of the buffer that returns the launch request's arguments, and whether it listens on a socket it names on its output (`:listens`, Delve: `dlv dap -l 127.0.0.1:0`, dialled with `make-tcp-connection`) rather than talking on its standard input and output. Heml knows lldb-dap for C and Rust (from PATH or `xcrun -f lldb-dap`; the program is asked for, offered as the file without its type, or cargo's `target/debug/<name>`), debugpy for Python (`debugpy-adapter`, or `python3 -m debugpy.adapter`; `file-launch`: the file itself) and Delve for Go (`outputMode: remote`, so that the program's output comes as events). One session at a time, `*dap*`, a `dap-session`: `dap-start` sends `initialize`, then `launch`, and configures -- `setBreakpoints` for each file, `configurationDone` -- when the adapter says it is `initialized`, but only once `launch` has been sent (`dap-configure`), since an adapter may say so before. `stopped` asks for the thread's frames and the top frame's first scope's variables, and then has the command loop (`queue-command`) show the place (`dap-show-stop`: the file, point at the line's code) and fill the buffer "Debugger" (frames, `>` the selected; variables, with `...` for those with parts; Return, "Debugger Select", selects a frame or shows a variable's parts under it). What the program prints, `output` events, goes to "Debug Output" from a scheduled event (`dap-idle`). Breakpoints are marks in `*breakpoints*`, sent as line numbers; a breakpoint is drawn as a red `●` in the fringe's first column and the selected frame's line as a green `▶` in its second (`dap-line-fringe`); `define-debug-adapter` gives its modes a fringe two columns wide. Requests the adapter makes (`runInTerminal`, `startDebugging`) are declined. Commands: "Debug" (F5, `C-c d d`: start, or continue when stopped), "Debug Toggle Breakpoint" (F9, `C-c d b`), "Debug Next" (F10, `C-c d n`), "Debug Step In" (F11, `C-c d s`), "Debug Step Out" (Shift-F11, `C-c d f`), "Debug Continue" (`C-c d c`), "Debug Pause" (`C-c d p`), "Debug Stop" (Shift-F5, `C-c d k`), "Debug Evaluate" (`C-c d e`, in the selected frame) and "Debug Show" (`C-c d w`); and a Debug menu. Traffic is logged with the language servers' (`HEML_LSP_LOG`, lines starting `dap`). `test/fake-dap.py` is the stand-in the smoke tests use, as Python's adapter; `make smoke-dap` (`test/smoke-dap.sh`) debugs a C, a Python and a Go program with the real adapters, skipping one not installed or, with `SMOKE_DAP_STRICT=1` as in CI, failing; debugpy is looked for in `build/debugpy-venv/` too.

**Processes and signals** (`ioconnections.lisp`). Every process Heml starts leads a session and a process group of its own (`setsid` in `%exec-in-child`): one on pipes, so that a program a debugger runs cannot take the editor's terminal; one on a pseudo-terminal (`make-process-with-pty-connection`) has it as its controlling terminal too (`TIOCSCTTY`; opening it after `setsid` does that on Linux but not on macOS), so the line discipline turns ^C, ^Z and ^\\ into SIGINT, SIGTSTP and SIGQUIT for the job in its foreground, a shell has job control, and a new size (`set-pty-size`, `TIOCSWINSZ` on the master) is SIGWINCH. The child blocks every signal and runs `without-interrupts` from the fork (ECL's took a SIGCHLD queued before the fork as an error, and sat in its debugger), and just before exec `reset-child-signals` sets each signal to its default and unblocks them all, as a shell would find them: exec keeps the mask and what is ignored. `connection-signal` sends a signal to a pty's foreground job (`tcgetpgrp` on the master) or a process's group (`killpg`); the shell's "Interrupt Buffer Subprocess" and its fellows use it, on `C-c C-c`, `C-c C-z`, `C-c C-\\` and `C-c C-d` in Process mode as in Emacs (they were stubs). An ended process is reaped (`waitpid`, `reap-process`; nothing did, and they were zombies), when its input ends (`note-process-ended`, before the sentinel hears `:disconnected`) or later from a scheduled event (`reap-later`, `*unreaped*`), and its exit code kept (128 and the signal's number for one a signal ended); deleting a connection hangs up a pty's group (SIGHUP) or asks a pipe's to end (SIGTERM), and kills it if it is still there three seconds on. Reading a pty whose other side has closed is its end (EIO on Linux). `ioctl` is variadic: on arm64 macOS SBCL must call it with `foreign-funcall-varargs` (a fixed third argument fails) and ECL through `c-inline`, and osicat's `ioctl` takes the request as a signed 32-bit number, too small for `TIOCSWINSZ`; on ECL osicat has no `TIOCSCTTY`.

**Scheduled events** (`invoke-scheduled-events`, `rompsite.lisp`): each event due is taken off the queue before it runs, and a repeating one put back first, so that a one-shot event (`schedule-event` with REPEAT NIL) runs once, and an event may schedule or remove events, itself too. (A one-shot event ran for ever, and the queue was bound to NIL while an event ran, so whatever it scheduled or removed was lost.)

**The terminal emulator** (`term.lisp`, the system `heml.term`): "Term" (also the Tools menu) runs "Term Program" or `$SHELL` (with an argument, asks) on a pseudo-terminal of its own, sized to the window, with `TERM=xterm-256color` and `COLORTERM=truecolor`, its termios left as made (`:terminal t`), in a buffer `*terminal*` in Term mode. libvterm emulates the terminal: what the program writes goes to `vterm-input-write` (the connection's filter), and `term-refresh`, at most every `*term-refresh-interval*` (1/60 s, and once more when output stops, a one-shot scheduled event), reads the rows libvterm damaged since the last refresh, and the cursor's rows old and new (`term-damage`, a `defcallback` whose VTermRect, four ints passed by value, arrives as two 64-bit integers, rows in the first; damage merged a row at a time and flushed after each write; every row after a resize or when the rows' count changes, `mark-term-all`), each cell by cell (`cells-text`: characters, combining characters, wide characters' right halves skipped, and fonts from each cell's attributes and colours, worked out only when they differ from the cell before) into the buffer's last rows, after the lines libvterm pushed off the top (`term-pushline`, kept in `term-pushed` until then), within "Term Scrollback" (10000). `term-screen-mark` (right-inserting, moved past the scrollback's new lines) marks the screen's first row, so nothing walks the scrollback; the buffer records no undo (`buffer-undo-p`), which was most of the time; point is put at the cursor and each window's display start at the screen's first row, as a terminal window shows it. A colour is Heml's palette index for 0-8, xterm's index past it (9, Heml's text colour, as RGB), or `(red green blue)`. Keys: in Term mode every character, Control-letter (but `C-c` and `C-x`, and `C-g`, which the editor takes as its abort before any key is looked up: `C-c C-g` sends it), Meta-character (but `M-x`) and named key goes to "Term Send Key", which turns the key into libvterm's (`vterm-keyboard-key`, `-unichar`) and its output callback (`term-output`) writes the bytes; `C-c C-c`, `C-c C-x`, `C-c C-z` and `C-c C-d` send those, `C-c C-j` (or `C-c Linefeed`, a terminal's ^J) is Term Copy mode, where the buffer is read and copied from and `q` or `C-c C-k` comes back, `C-y` (and Super-v) pastes bracketed, and `C-c M-x` or `C-c x` is `M-x` (in a terminal Heml, Meta is Escape and a key, and Escape goes to the program, as vim wants). The window's size is followed (`term-idle`, a scheduled event, `vterm-set-size` and `set-pty-size`), with libvterm's reflow, so that a narrower terminal wraps its lines rather than cutting them off; the title (`term-settermprop`) is kept; when the program ends, `[The program ended with code N.]` is written into the terminal itself; killing the buffer hangs its processes up, closes the pseudo-terminal (after the program has ended too) and frees libvterm's. libvterm's callbacks are `cffi:defcallback`s given the terminal's number as user data; ECL needs them compiled, as ASDF does.

**Spelling.** The dictionary is built in memory from `resources/spell-dictionary.text`, which `spell-build.lisp` reads into the image at compile time (`build-dictionary-in-memory`): its hashes are the Lisp's own `sxhash`, so no binary file travels between Lisps. In Text mode with Spell mode on, `text-highlight-line` (`spellcoms.lisp`) underlines each word the dictionary lacks in red, and shows links.

**Shells and interactive buffers.** `get-interactive-input` records where each input began ("Input Starts"): `C-c C-p` and `C-c C-n` ("Previous Prompt", "Next Prompt") move between them, and Return on an earlier input sends it again. A shell buffer keeps at most "Shell Output Limit" lines (20000), trimming its start, and a carriage return in its output clears the output line, not the line at point.

**Links** (`exp-syntax.lisp`): `line-links` finds a line's links in its text (Markdown `[text](url)`, `<url>`, bare URLs, trailing punctuation trimmed), and each is drawn in `link-font`, a font whose `:link` key holds the target. Tree-sitter's `line-fonts` lays links over its colours; a mode with no highlighter gets `highlight-links`, which leaves alone a line with font marks of its own (a shell's colours). The TTY sends a font with `:link` as an OSC 8 hyperlink. "Open Link" (`C-c C-o`, `morecoms.lisp`) follows the link at point (`link-at-mark`): a web or mail address with `open`, a file by visiting it; in Cocoa, Command-click does ("Mouse Open Link").

**Choosing a mode for a file** (`process-file-options`, `filecoms.lisp`; by hand, each language mode has a command, "Shell Script Mode", "Rust Mode" and so on, made in a loop at the end of `tree-sitter-modes.lisp`): a `-*- Mode: … -*-` line wins; otherwise the file's name, through `define-file-name-mode` (`.zshrc`, `.bashrc`, `.env.*` and the like are Shell Script, `.babelrc` JSON, `.clang-format` YAML, `.sbclrc` Lisp; a `*` in a name stands for any characters; "Mode from File Name" turns it off); otherwise the file's type, through `define-file-type-hook`; otherwise, for a file without a type, the interpreter its `#!` line names, through `define-interpreter-mode` (`#!/bin/sh` and `#!/usr/bin/env bash` are Shell Script, `python3` is Python, `sbcl` is Lisp; a version such as `python3.12` is dropped). `define-comment-syntax` (`tree-sitter-modes.lisp`) sets a mode's "Comment Start", "Comment End" and "Comment Begin".

**Dired** (`diredcoms.lisp`, with file operations in `dired.lisp` and the listing in `print-directory-verbose`, `filecoms.lisp`). A Dired buffer is a header line and then a line per file, in the order of `dired-info-files`; `dired-file-at` and `dired-file-line` map between them, skipping `+dired-header-lines+`. Files whose names start with a dot are listed when "Dired Show Hidden Files" is true, as it is by default; `h` shows or hides them in one buffer (`dired-info-dot-files-p`), and an argument to "Dired" does what the variable does not. A file's first column shows its state: `D` flagged for deletion (`dired-file-deleted-p`), `*` marked (`dired-file-marked-p`). Operations act on `dired-targets`: the marked files, or the one under point. `update-dired-buffer` keeps marks, flags and point's file. Deleting moves files to the Trash with `/usr/bin/trash` where it exists ("Dired Delete to Trash"). A scheduled event (`start-dired-watch`) calls `maintain-dired-consistency` every two seconds, which lists a directory again when `dired-directory-signature` (its modification time and size, since the time is kept to the second) has changed. `*directory-sort*` orders the listing by name, date or size. `i` lists a subdirectory inline (`dired-info-expanded`): `dired-listing` puts its entries after its line, named from the top directory (`sub/file`, through `*directory-name-prefix*`), so each line is still one file. `C-x C-q` switches the buffer to Wdired, a major mode of its own so that letters are letters, keeping the buffer's `dired-information`; `C-c C-c` renames each file whose name its line now shows differently (`dired-line-name`), and `C-c C-k` goes back to Dired. The watcher leaves a Wdired buffer alone. `define-mode-highlighter` colours Dired's lines (`dired-highlight-line`).

**Bufed** (`bufed.lisp`, `C-x C-b`) lists the buffers under a header, one a line: a mark column (`*` marked, `D` flagged), then `.` current, `%` read-only and `*` modified, and the name (just the file's name when the buffer has the default name for its file), size, mode and file. The list is made again from the buffers (`bufed-fill`) whenever it is shown; `*bufed-lines*` holds what each line after the header shows, an entry or NIL for a group's heading; marks live in `*bufed-marks*`, by buffer, so they survive. Operations act on `bufed-targets`. `*bufed-sort*` (recency, from `*buffer-history*`; name; size; mode), `*bufed-filter*` (a mode's name, which wins over name text, `*` for modified, or text in names) and `*bufed-grouped*` (by directory) shape it. Buffer hooks only mark it stale; a scheduled event makes it again within a second while it is shown.

**Menus** (`menus.lisp`) are data, for whichever frontend shows them: `define-menu`, `add-menu-item`, `remove-menu-item`, `remove-menu` and `define-context-menu`, exported from `heml-interface`, change `*menus*` and `*context-menus*` and call the functions in `*menu-change-functions*`. An entry is `(title action &key key modifiers hidden)` or `:separator`; the action is a command's name, `(:command name arg ...)`, or what only a frontend can do (`(:call function)`, `(:selector "name:")`, `(:font-size n)`, `:services`). A menu's `:mode` shows it only in that major mode's buffers; its `:role` (`:application`, `:windows`, `:help`) is for the frontend. The built-in menus are defined there. "Menu Bar" (`M-\``) picks a menu and an item in the echo area, the terminal's way to them.

**The Cocoa backend's threads.** AppKit must own the main thread, so `invoke-with-editor-thread :cocoa` (`cocoa-main.lisp`) runs `[NSApp run]` there and runs the whole editor session on a thread named "Heml". The two threads never share Heml state:
- Input: `-keyDown:` posts plain descriptors to an inbox and writes a byte to a pipe. The pipe's read end is an ordinary iolib connection, and its filter turns the descriptors into key-events on the editor thread.
- Output: the device's redisplay methods copy dis-lines into the screen (a locked grid of rows). When a pass is finished, `device-force-output` calls `present-screen`, which copies the rows and cursor into the screen's `shown-` slots, and `-drawRect:` paints only those. So the view never shows a frame half drawn.
- Typing: named keys, and keys with Control or Meta, are posted directly from `-keyDown:`. Everything else goes through `-interpretKeyEvents:` and the view's `NSTextInputClient` methods, so dead keys and input methods work. Only the left Option key is Meta by default.
- The clipboard: `*interprogram-cut-function*` and `*interprogram-paste-function*` (`killcoms.lisp`) join the kill ring to the pasteboard. Kills and "Save Region" call the first; "Un-Kill" calls the second, and uses the pasteboard only if its change count shows another application wrote to it. The Edit menu posts Super keys, which `install-mac-bindings` binds.
- Menus are Heml's (`menus.lisp`, below); Cocoa adds its application and Window menus and its Mac-only items through the same API, and `rebuild-main-menu` builds the menu bar from `copy-menus` on the main thread whenever `*menu-change-functions*` says they changed. A mode's menu is shown only while the current buffer is in that major mode: each frame carries the mode (`screen-mode`, left alone while the echo area prompts), and `present-screen` has the main thread call `show-mode-menus` when it changes. The item's tag indexes `*menu-actions*`. A command is posted as `(:command name arg ...)`: the editor queues it in `*menu-commands*` and then the `Menucommand` key, and the "Menu Command" command runs it. So a menu item runs inside the command loop, with prompts, undo and errors behaving as they do for a typed key.
- Files from Finder arrive at the app delegate's `application:openURLs:` and are visited through `process-command-line-argument`.
- Fonts: fonts belong to the main thread. `change-font` re-measures the cell and posts a `:resize`, and it saves the choice in `NSUserDefaults`. The View menu's items target the app delegate, not the responder chain, so their shortcuts work whatever has focus.
- Anything AppKit must do for the editor thread goes through `on-main-thread`.

**Window layout** is shared by every device (`layout.lisp`). The windows other than the echo area tile a rectangle, and `device-layout` holds that as a tree: each leaf is a hunk, and each split divides its space into rows or side-by-side columns, with a size for each child. Side-by-side windows are divided by a column that neither owns, and each device draws a bar there. The shared `device-make-window`, `device-delete-window` and `device-enlarge-window` methods change the tree. `apply-layout` then sets every hunk's geometry, resizes each window's image to fit, and rebuilds the ring of hunks in tree order, which is the order `next-window` follows. `resize-device-layout` handles a new screen size. A device only supplies `device-make-hunk` and draws each hunk where the hunk says: `device-hunk-column` and `device-hunk-width` give its columns, its `position` is its modeline row, and its text starts at `text-position - text-height + 1`. `C-x 3` is "Split Window Horizontally", `C-x {` and `C-x }` shrink and enlarge a window horizontally, `C-x 1` is "Delete Other Windows", and `C-x +` is "Balance Windows" (`balance-layout`), which sizes each split's children by how many windows lie across each one.

**The mouse.** Heml represents the mouse as key-events with mouse keysyms: `Leftdown`, `Leftup`, `Leftdrag`, `Scrollup`, `Scrolldown` and the others in `keysym-defs.lisp`. A backend queues each one with `q-event`, passing the X and Y within the window's text (Y is NIL on a modeline) and the hunk. Pointer commands read them back with `last-key-event-cursorpos`. The Cocoa view posts grid cells, and `locate-cell` on the editor thread turns them into those coordinates. On its first entry, Cocoa rebinds the left button to the "Mouse ..." commands in `morecoms.lisp`, and gives the active region the `:selection` background. The active region is drawn with font marks (`highlight.lisp`), told to the line image as `*region-font-marks*` and `*region-font*` (`linimage.lisp`): `mark-display-font` draws each font mark inside the region in its font under the region's (`merge-region-font`: the region's keys win, so its background shows and the token keeps its colour; a region font that is a number, as the TTY's is, replaces it), and the region's own marks over the token font in effect there. A syntax colour's mark used to end the region's font, so highlighting drew over the selection. Dragging the bar between side-by-side windows, or a modeline, resizes windows: `drag-border` (`cocoa-device.lisp`) intercepts that press and its drags before they become keys, and moves the edge with `layout-move-edge`. Each frame also carries the draggable edges (`layout-borders`) to the main thread, where `-resetCursorRects` gives them resize cursors.

**Where Heml keeps things** follows the XDG Base Directory specification (`main.lisp`): `heml-config-directory` is `$XDG_CONFIG_HOME/heml/` (`~/.config/heml/`), `heml-state-directory` `$XDG_STATE_HOME/heml/` (`~/.local/state/heml/`), and `heml-data-directory` `$XDG_DATA_HOME/heml/` (`~/.local/share/heml/`); a variable unset, empty or relative is ignored. The init file is `~/.config/heml/init.lisp`, or failing that the older `~/.heml.lisp`, `~/.heml/heml.lisp` or `~/.heml-init.lisp` (`init-file-names`, `init-file`). The Cocoa app's Settings… opens `init-file`, making its directory.

**The environment and file names.** An app started by Finder has the system's short `PATH`, so, as Emacs's exec-path-from-shell does, `maybe-import-shell-environment` (`main.lisp`, before the init file is loaded) runs the user's login shell (`login-shell`: `$SHELL`, or the password file's) as `-l -i -c /usr/bin/env` and sets `*shell-environment-variables*` (`PATH`, `MANPATH`, the locale and the agents' sockets) in the process, which the programs Heml runs inherit; `*import-shell-environment*` is `:auto` (only when there is no `TERM`, that is, not started from a terminal), T or NIL, and "Import Shell Environment" does it again. "Shell Utility" is NIL for the user's own shell. `heml-ext:expand-file-name` reads a file name as a shell would: `~` and `~user` are home directories (`isys:getpwnam`), and, since a file prompt starts with a directory in it, a `~` after a `/` or a second `/` starts the name again, as in Emacs. The file prompt (`file-verification-function`), file completion (`complete-file`), `find-file-buffer`, a shell buffer's filename completion and "Open Link" all go through it.

**Things for the command loop to do.** `queue-command` (`command.lisp`) takes a function and queues the key `Queuedcommand`, bound to "Queued Command", which calls it: for what happens while events are handled and wants to prompt or show a popup, as a language server's question does. When that key comes part way through a key sequence the command loop calls the function itself and the sequence goes on (`%command-loop`); and while the echo area is asking something the function waits, and is called after the command that asked (`run-waiting-commands`, on "After Command Hook"), since it might take the editor away from the prompt. A keysym's number must be its own: `keysym-defs.lisp` lists them, and one given twice is silently the other key.

**Reading a file** (`read-file`, `files.lisp`) notes the whole of what it read for undoing once: noting each line took time as the square of the file's length, since a place is noted as a line's number, counted from the start.

**Extending the editor.**
- A variable's or a command's name is a string literal: never change one in place (`canonical-case` copies; it once upcased its argument, which renamed a command that shared a variable's name).
- Commands are defined with `defcommand "Name" (p) ...`, which produces a function called `name-command`.
- Editor variables are defined with `defhvar`.
- Keys are bound with `bind-key "Command Name" #k"control-x"`.
- Modeline fields come from `make-modeline-field` (`window.lisp`).

Useful globals include `hi::*buffer-list*` and `hi::*window-list*`.

**Characters.** Buffer lines are full `character` strings, and files are read and written as UTF-8. Heml shadows `char-code-limit` as 256 in `heml-ext` and `hi`, so a table indexed by character code covers only the first 256 codes. Past that, character sets fall back to a hash table (`char-set-ref` in `charmacs.lisp`), and so do `char-key-event` and the Boyer-Moore jump tables, which use the low byte. Don't declare a `base-char`: on SBCL that means ASCII.

A key for a character past ASCII comes from `heml-ext:character-key-event`, which makes the key-event on first use. Its keysym is the code point for Latin-1, and `#x01000000` plus the code point past that, as in X11, so it can't collide with the special keys at `#xFF00`–`#xFFFF`. `*new-character-key-event-hook*` then binds it to Self Insert (`bindings.lisp`). Keysyms past 16 bits live in `*large-keysym-key-events*`. A wide character (East Asian Width W or F: CJK, fullwidth forms, most emoji) is displayed as itself followed by `wide-character-filler` (`linimage.lisp`). This goes through the same print-representation mechanism that shows a control character as `^X`, so everything that counts columns counts two. The character sets fill those entries lazily through `character-set-default-function` (`charmacs.lisp`). A device draws the character across both cells and nothing for the filler: TTY's `device-write-string` skips it, and so does Cocoa's `draw-text`.

**Font numbers are colours.** A font number in a font-change is an ANSI colour index, or a property list such as `(:fg 7 :bg 4 :bold t)` (`*modeline-font*` in `window.lisp`), whose keys are `:fg`, `:bg`, `:bold`, `:italic` and `:underline`. The TTY and Cocoa backends both read them that way. A colour is Heml's palette, 0 to 9 (9 is the text's own colour), an index among xterm's 256 past it, or `(red green blue)`, as a terminal's text has: Cocoa makes those NSColors (`xterm-rgb`, `color-name-for`), and the TTY gives the terminal the index when it has 256 colours, an RGB colour's nearest (`rgb-xterm-index`), or with eight the nearest of those (`tty-color`). Cocoa also knows the colour names `:selection`, `:accent` (`controlAccentColor`, the accent the user chose in System Settings) and `:accent-text` (`alternateSelectedControlTextColor`), and on starting sets `*modeline-font*` and `*popup-selected-font*` to `(:fg :accent-text :bg :accent :bold t)`, so the modelines and a popup's choice are in the accent colour (the TTY keeps blue); these are dynamic colours, resolved as they are drawn, and the view draws again on `NSSystemColorsDidChangeNotification`, so changing the accent shows at once. Cocoa keeps italic and bold-italic fonts beside the regular and bold ones (`install-fonts`); a font with no italic face is slanted instead (`NSObliqueness`, recorded in `display-slanted`). It draws an underline itself, a line at the baseline the width of the run's cells, rather than asking AppKit for one.

**Slave Lisps.** The binary re-executes itself with `--slave` to create eval-server slaves, which it talks to over `wire`. See `eval-server.lisp`, `lispeval.lisp` and `slave-list.lisp`.

**Terminals.** `heml.terminfo:tparm` evaluates terminfo string expressions, including the `%? %t %e %;` conditionals that every 256-colour terminal's `setaf` uses. Its binary operators pop their second operand first. The terminal's erase character (`*tty-erase-char*`, usually `^?`) is Backspace, whatever terminfo's `kbs` says. The TTY's `listen-editor-input` (`tty-input.lisp`) reads what the terminal has and says NIL, so redisplay never gives way to typeahead (saying whether a key was queued made a terminal's echo wait for every key typed after it, three times as long under ECL); the input loop (`%editor-input-method`) looks at its queue itself before it waits, since a key can be queued while the screen is drawn (`linedit-redisplay` dispatches events), and it waited for the next. `setup-input` (`tty-disp-rt.lisp`) leaves `IEXTEN` on, so it disables VLNEXT, VDISCARD and VSTATUS itself. Otherwise the driver would swallow `C-v`, `C-o` and `C-t`. `linedit-device`, the `:mini` backend in `linedit.lisp`, has its own `device-init`, which starts without the alternate screen; the full-screen TTY editor uses the alternate screen. Shell buffers turn SGR colour sequences into font marks and drop other escape sequences (`write-shell-output` in `shell.lisp`).

**CI.** `.github/workflows/ci.yml` runs on a macOS runner, which has a window server. It checks out the submodule, sets up ocicl for SBCL and ECL, runs `make smoke`, `make smoke-tty` and `make smoke-tty-ecl`, installs the language servers Homebrew has and runs `make smoke-lsp` with `SMOKE_LSP_STRICT=1`, then the debuggers and `make smoke-dap`, then Node 24 and `make smoke-run`, each strict, and `make smoke-git`, builds and checks the app ad hoc, makes its disk image, and starts and quits the app. It uses Homebrew's SBCL, which links libzstd, so that bundle is for testing only. `.github/workflows/release.yml` runs on a tag `v*`, or by hand as a dry run. It builds SBCL `--without-sb-core-compression` (cached), then on arm64 and Intel runners signs with the Developer ID from the secrets, notarises and staples the app and the disk image, and publishes a release with both images.

## Other directories

- `unused/`: dead code (an elisp VM experiment, old spell, gosmacs). It isn't loaded by any system.
- `doc/`: the original Hemlock manuals in Scribe (`doc/user`, `doc/cim` = Command Implementor's Manual). This is the authoritative reference for the extension API. The manuals keep Hemlock's names: read `hemlock:` and `hemlock-internals` as `heml:` and `heml-internals`.
- `doc/heml-internals.org`: internal notes.
- `doc/roadmap/heml-roadmap.org`: goals and the known bug list.
